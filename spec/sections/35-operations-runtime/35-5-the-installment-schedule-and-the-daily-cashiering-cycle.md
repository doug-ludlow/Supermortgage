### Blueprint row
Sections 2.1, 2.3 and 2.7 are built as engines: the Allocation Engine, the autodraft machine and the late-charge test each take a `LoanCashState` and return a plan, and the runtime's daily pass (`servicingDailySweep`, src/runtime/servicing.ts:130-170) drives them for a loan by synthesising a level fixed-rate schedule from `loan_terms` on every pass (servicing.ts:85-89) and posting whatever `payments` rows the borrower's in-app command wrote. Four things stop this being the subservicing business. (1) No deployed code writes `loan_installments`: neither `POST /v1/applications/{id}/fund` (src/runtime/origination.ts:161-190 writes `loans`, `loan_terms`, borrowers and custodial rows only) nor `POST /v1/transfers/batches` (src/runtime/transfers.ts:130-150, the same set) inserts a schedule row; the only INSERT in non-test source is the borrower journey fixture (src/runtime/borrower/fixtures/journey.ts:507), so the delinquency counter job, which JOINs `loan_installments` (src/runtime/delinquency.ts:40-43), selects zero hosted loans and no Reg X window, day milestone or 120-day gate ever opens (gap "Amortization / installment schedule", blocking). (2) The sweep iterates only `loans WHERE origination_application_id IS NOT NULL` (servicing.ts:133), so every transfer-boarded loan — the 100-loan demo book, every partner-book loan, the whole subserviced book — never sees 2.1 posting, a 2.7 run or a 2.3 amount-change check from the scheduler (gap "Cashiering sweep scope excludes the subserviced book", blocking). (3) The only source of received cash is the 32.2 in-app payment command (src/app/tools/section32-2.ts:600-612); no lockbox file is ingested (the lockbox port is touched only by `lockbox.image_ocr`, section02.ts:45,99), no ACH file is built and transmitted on a schedule, no NACHA return file is processed, and the FAKE bank ports are constructed per `Runtime` (src/runtime/app.ts:126-131) so the sweep job and the API service do not share a fake bank (gap "Payment intake and money movement", blocking). (4) Every loan's civil day is `America/Phoenix` (delinquency.ts:27 `LOAN_LOCAL_TZ`) and every notice's servicer block is the fixture constant `SERVICER_CONTACT` (servicing.ts:46: "Supermortgage LLC", TIN 12-3456789, PO Box 1 Testville TX), so day counts and notices are wrong for any loan outside that assumption (gap "Real-loan configuration", minor). This process writes the schedule for every loan at boarding and re-projects it on every terms change, runs the three cashiering steps for every active loan as one 35.3 unit per loan per day, ingests the lockbox file, builds and transmits the ACH file and actions the return file as cycles with receipts, and replaces the two constants with per-loan configuration rows and an effective-dated servicer profile.

### Verified requirement (as of 2026-09-15)
**The schedule is 2.1's projection, and 2.1 fixes its arithmetic (spec/sections/02-payment-processing-cashiering/2-1-*.md:120, :126; F-1-09).** Interest for the installment due on `d` = `round_half_up(UPB_as_of_LPI × note_rate / 12)`; principal = P&I − interest, "the last installment absorbs rounding"; P = `loan_terms.pi_cents + loan_terms.escrow_payment_cents`, effective-dated. `loan_installments` is declared a projection with primary key `(loan_id, due_date)`, `pi_cents`, `interest_cents`, `principal_cents`, `escrow_cents`, `status` ∈ {due, satisfied, prepaid, deferred, forborne}, `satisfied_on`, `credited_as_of`, `late_charge_state` (db/migrations/0003_cashiering.sql:104-117). The level payment is `round_half_up(UPB × r × (1+r)^n ÷ ((1+r)^n − 1))` at fixed decimal scale (src/kernel/money/cents.ts:54-62 `levelPayment`); 1.1 HF-005 recomputes a tape's fixed-rate P&I with precision 20 and a $0.01 tolerance (spec 1-1-*.md:107). **VERIFIED** at HEAD.

**An ARM's schedule changes only at a change date, by 7.2's figures (spec/sections/07-*/7-2-*.md:101).** New P&I = `UPB × r ÷ (1 − (1+r)^−n)` on the expected UPB at the change date over the remaining term; the worked example (Plan 4927, $400,000.00 at 5.750%, 360 months, first payment 2021-12-01) gives P&I $2,334.29, expected UPB after the 2026-11-01 payment $371,048.86, new rate 6.375% and new P&I $2,476.44 from 2026-12-01 — the row-by-row half-up schedule of rule 2 reproduces all three to the cent (worked example C). `loan_terms` carries the ARM fields (`arm_index`, `arm_margin_bps`, caps, `arm_next_change_date`, `arm_change_frequency_months`, 0001_baseline.sql:139-172) and both boarding paths write them (transfers.ts:140-147; origination.ts:184-188). **VERIFIED.**

**Both boarding paths run 1.1's `BoardingService`, which appends `loan.boarded` (src/domain/boarding/service.ts:332-357).** The transfer route (transfers.ts:130-183) and the fund hand-off (origination.ts:161-190 via `boardFundedApplication`) each commit the `loans` and `loan_terms` rows in one transaction with the event; nothing in either writes `loan_installments`. The trigger event for the schedule clock therefore exists on both paths. **VERIFIED.**

**The sweep's loan selection and the state it hands the engine (src/runtime/servicing.ts:67-140; src/app/tools/section2-1.ts:33-43).** `loanCashState` builds `LoanCashState` from `loans`, `loan_terms`, the ledger balances and the entity store's `payments` and `fees`, projecting installments on the fly as `pi_cents` from the latest `loan_terms` row for every month from `first_payment_date` (servicing.ts:85-89 — a fixed-rate assumption applied to ARM loans too); `payments.read/write{op=post}` requires `input.state` ("post needs the loan's cash state", section2-1.ts:38), so a hosted caller can supply its own figures. The selection at servicing.ts:133 excludes loans without `origination_application_id`. **VERIFIED.**

**Receipt date and the cut-off are per channel and local (2.1 rule 1; Reg Z §1026.36(c)(1)(i) and comment 36(c)(1)(i)-3).** Lockbox items scanned after the 5:00 p.m. local cut-off are dated the next business day; our originated ACH debits are received on the settlement date; `payment_channels.cutoff_time` and `cutoff_tz` hold the written cut-off (0003_cashiering.sql:70-75, default `America/New_York`). The Reg X §1024.39 day count and 11.1's "00:05 loan-local" counter job (spec 11-1-*.md:62) need a loan-local civil date; the runtime hard-codes it (delinquency.ts:27). **VERIFIED.**

**Returns (2.3 rule 7; Nacha Operating Rules, verified by 2.3 on 2026-09-09).** R01/R09: reverse the payment (2.1 rule 9), assess the NSF fee where 2.7 rule 7 permits (`jurisdiction_rules.nsf_fee.allowed`, `min(2,500¢, cap)`), notify the borrower, reinitiate once automatically 3–5 banking days later with company entry description "RETRY PYMT" if the borrower has not otherwise paid and the loan is not on hold, at most two reinitiations within 180 days (`NACHA_NSF_REINITIATION_180_MAX2`); R02/R03/R04/R20 terminate the account, no reinitiation; R05/R07/R10/R29 are unauthorized — cancel the enrollment, open a fraud case; R11 is our error — the corrected entry within 60 days (`NACHA_R11_CORRECTED_REINITIATION_60`), no fee. 2.3's schedule row names `autodraft.file.build` "daily at 14:00 ET for entries settling T+1/T+2" (spec 2-3-*.md:52). **VERIFIED** against the spec; the Nacha day-count for the automatic retry (3–5 banking days) is 2.3's **[PARTIALLY VERIFIED]** and is inherited here as policy 3 banking days.

**Servicer identity in notices (Reg X §1024.35(c)/§1024.36(b) exclusive address; Reg Z §1026.41(d)(6) contact information; A2-1-01).** A servicer that designates an exclusive address for notices of error and information requests must state it on the periodic statement and in the hello notice; the statement carries the servicer's toll-free number and, if applicable, an e-mail or web address; every borrower-facing notice the platform renders reads these from `SERVICER_CONTACT` today. The go-live values (legal name, NMLS ID, TIN, the P.O. boxes) are the licensing workstream's (31.x) — **[UNVERIFIED: the FAKE profile's values are the authored samples' and must be replaced before any real notice]**.

**Discrepancies vs blueprint**: (1) The gap assessment's "synthesizes a fixed-rate level schedule on the fly" is exact and is the reason ARM loans post the wrong interest after a change date: servicing.ts:85-89 uses the latest `pi_cents` for every month, past and future, and never re-derives the interest split from the schedule; the build reads `loan_installments` (rule 4) and deletes the projection loop. (2) 35.3 names this cycle `cashiering_daily` with receipt literal `cashiering.daily.run_completed` (35-3-*.md:75); an earlier draft of 35.4 spelled the same receipt `cashiering.cycle.run_completed`; 35.4's `eod_cutoff` step now waits on `cashiering.daily.run_completed` (35-4-*.md rule 1). This process emits 35.3's spelling — the registry def owns the literal. (3) The §35 plan (written at d1238cc) put the "money spine" — §2 projectors, server-side cash state, refusal of client-supplied state — in its 35.1 lane ("3a"); at HEAD 35.1 owns the projectors and `entity_projections` while the state refusal (`NO_CLIENT_STATE`, rule 5) and the schedule are this process's, because they are cashiering's facts. (4) 2.3 rule 3 sets the ACH settlement day and 2.3's schedule names the file build; neither the spec nor the tree gives the build a timer or a runner — the daily build, transmit and return ingest are registered here as three 35.3 cycles under the `cashiering` agent, referencing 2.3's timers (`FNMA_C1103_DRAFT_BY_PENALTY_FREE_DATE_GATE`, `REGE_1005_10D_VARIABLE_AMOUNT_NOTICE_10`, `NACHA_WEB_ACCOUNT_VALIDATION_GATE`, `NACHA_NSF_REINITIATION_180_MAX2`) without redefining them. (5) 2.1's `FNMA_C1101_LOCKBOX_CLEARING_1BD` is the deposit clock (cash reaches `clearing_cash`); this process adds the posting clock (`SM_LOCKBOX_BATCH_POSTED_1BD`: every item posted or in 6.5's suspense) because a deposited-but-unposted batch is the credit-as-of-receipt failure the Guide breach clock does not see. (6) The demo book comment "AZ book: America/Phoenix" (delinquency.ts:26) describes the 100-loan fixture only; the fixture's `properties.state` column is what rule 9 maps from, so the fixture keeps its zone without a constant.

#### State machine
Per installment (`loan_installments.status`): `due` —(`payment.posted` applying it; 2.1)→ `satisfied` | —(`payment.prepaid.applied`)→ `prepaid` | —(12.x deferral / forbearance terms)→ `deferred` | `forborne`; `satisfied` —(`payment.reversed` naming it)→ `due` (the row's `satisfied_on`, `credited_as_of`, `satisfied_by_payment_id` cleared, the transition logged as `installment.restored`); `deferred` / `forborne` —(new terms)→ `due`. Terminal: none (a paid-off loan's rows are all `satisfied` or `prepaid`). The agent performs every transition through 2.1's commands; no human edits a row.
Per schedule run: `written` (terminal; a reprojection is a new run). Per cashiering unit: `planned` (35.3 job) → `done` | `skipped_hold` | `failed` → (35.3 retry) → `dead`. Per lockbox batch: `received` —(every item identified or in suspense, variance 0)→ `posted`; `received` —(Σ items ≠ control total)→ `variance` —(`officer` resolves the item)→ `posted`. Per ACH entry (2.3's `ach_entry_status`): `built` → `transmitted` → `acknowledged` → `settled` → `returned` —(R01/R09, retry allowed)→ a new `built` reinitiation entry with `reinitiation_of_entry_id`. Per servicer profile: `draft` —(`compliance` approval)→ `active` —(a later version's `effective_from`)→ `superseded`.

No override changes an installment's money.

#### Business rules and calculations
1. **The schedule is written in the boarding transaction, for every loan, on both paths.** `installments.write` runs inside the same unit of work as `loan.boarded` (transfers.ts:130-183; origination.ts:161-190): one `installment_schedule_runs` row and one `loan_installments` row per remaining installment from the first unpaid due date (`next_due_date` on a transfer tape; `first_payment_date` at fund) to `loan_terms.maturity_date`, computed from the boarded `loan_terms` (`note_rate_bps`, `pi_cents`, `escrow_payment_cents`, `amortization`, `interest_method`) and the boarded UPB (the tape's UPB as of the LPI; the note amount at fund). A boarding that cannot write the schedule refuses the board (`SCHEDULE_REQUIRED`) — no `loans` row is committed without its rows. `installment.schedule.written` satisfies `SM_INSTALLMENT_SCHEDULE_AT_BOARD_0` in the same commit.
2. **Row arithmetic (2.1 rule 5, F-1-09; rule set `cashiering.schedule.v1`).** For row k with opening UPB `U_k` and monthly rate `r = note_rate ÷ 12` (decimal, precision 30): `interest_k = round_half_up(U_k × r)` (bigint cents via `divRound(U_k × rate_bps, 12 × 1,000,000)` half-up); `principal_k = pi_cents − interest_k`; `U_{k+1} = U_k − principal_k`; `escrow_k` = 3.6's effective escrow portion for the due date (`escrowPortionOn`); the final row's `principal = U_n` and its `pi_cents = interest_n + U_n` (`absorbs_rounding = true`), so Σ principal = the opening UPB exactly. The level payment at fund is `levelPayment(U_1, rate, n)` (cents.ts:54-62) and is compared with the note's P&I: a difference > 1¢ refuses the board (HF-005's tolerance). Interest-only, step, buydown and balloon amortizations project the scheduled payment of each period from `loan_terms` and 1.1's tape fields; `interest_method` other than `30_360` is a 4.1/16.1 daily-interest concern and does not change the row (the row is the contractual installment).
3. **An ARM's rows change only at a change date, from 7.2's figures.** At boarding an ARM's rows through the installment before `first_new_payment_due` carry the current rate and P&I; rows from `first_new_payment_due` onward are projected at the current rate too (the contract's payment until the change) and flagged by `rate_bps`. When 7.2 activates the adjustment (`loan_terms.version.activated{version, effective_on = first_new_payment_due, rate_pct}` — 7.2's own spelling, ops-7-2.ts:486 — with the new `note_rate_bps` and `pi_cents`), `installments.reproject` replaces every `due` row with `due_date ≥ effective_from` from the expected UPB 7.2 computed (`arm_adjustments.expected_upb_cents`) and keeps every `satisfied` / `prepaid` row untouched; the run records `rows_replaced`, `rows_kept` and the prior values. The same reprojection serves 2.4's re-amortization (Form 181), 12.x modifications, 3.x escrow changes (escrow column only) and 4.1 corrections. `SM_INSTALLMENT_REPROJECT_1BD` is satisfied by the run; a reprojection that would change a `satisfied` row is refused (`SATISFIED_ROW_FROZEN`) and escalated to `officer` — a satisfied row changes only through 2.1's reversal.
4. **The engines read the schedule; nothing projects on the fly.** `loanCashState` (servicing.ts:67-93) builds `installments` from `loan_installments` (`status`, `pi_cents`, `escrow_cents`, `satisfied_on`, `credited_as_of`, `satisfied_by_payment_id`) and the projection loop at servicing.ts:85-89 is deleted; the interest split 2.1 posts for an installment is the row's `interest_cents` when the loan's UPB equals the row's `upb_before_cents`, else recomputed by rule 2 from the actual UPB (a curtailment between rows) and the difference recorded on the run. 2.1's `payment.posted` and `payment.reversed` move the row status through `installments.satisfy` / `installments.restore` in 2.1's transaction. 11.1's counter job (35.9) and 7.1's statement (35.3's `statements` unit) read the same rows.
5. **Server-side state, refused from the client (`NO_CLIENT_STATE`).** `payments.read/write{op=post}`, `fees.assess{op=daily_run}` and `autodraft.read/write{op=amount_change_check}` derive `LoanCashState` inside the command from the typed rows (rule 4) — the hosted route strips or refuses an `input.state` / `input.custodial` (typed refusal, no write), so a caller cannot post against its own figures; the in-memory unit harnesses of §2 keep passing state (they are the engines' own tests). The per-loan custodial accounts come from `custodial_accounts` by `partner_party_id`.
6. **One unit per loan per day, over the whole book (`cashiering_daily`).** The 35.3 selector is `SELECT id, time_zone FROM loans JOIN loan_servicing_configs … WHERE boarded_at IS NOT NULL AND status NOT IN ('paid_off','transferred_out','repurchased','charged_off')` — no `origination_application_id` condition (servicing.ts:133 is deleted). `cashiering.run_unit{loan_id, as_of_date}` computes `local_date` = the loan's civil date for the planner's `as_of` instant in its `time_zone` (rule 9) and runs, in one unit of work: (a) 2.1 `payments.read/write{op=post}` for every `payments` row in `received` / `identified` for the loan, in receipt order (a partial opens 2.2's suspense item); (b) if a row's `due_date = local_date`, emit `installment.due_date_reached` and, if `local_date` is the day after 2.7's grace end for any `due` row, 2.7 `fees.assess{op=daily_run}`; (c) 2.3's amount-change check for every active enrollment whose next draft is within 31 days (servicing.ts:150-168, unchanged); then one `cashiering_unit_runs` row and `cashiering.unit.completed`. A loan under a `payment_holds` row that 2.1 treats as a hold still posts to suspense and records `skipped_hold` for steps (b)–(c). The unit is idempotent by `(loan_id, as_of_date)`: a second run the same day posts nothing, assesses nothing and records nothing new. The receipt election emits `cashiering.daily.run_completed{as_of_date, loans, posted, late_charges_assessed, amount_change_checks, units_dead}` once (35.3 rule 5); it satisfies `SM_CASHIERING_DAILY_RECEIPT_1D` and is 35.4's `eod_cutoff` receipt.
7. **Lockbox ingest (`lockbox_ingest`, per lockbox per servicer business day).** `lockbox.ingest` fetches the day's remittance file and images through the `lockbox` adapter, stores the file (35.2 `documents.store`, `sha256`), writes `lockbox_batches` and one `lockbox_items` row per detail line, and refuses to post when Σ `amount_cents` ≠ the file's control total (`status = variance`, `officer`). Per item: `received_on` = the lockbox agent's receipt date, or the next servicer business day when `scanned_at` is after `payment_channels.cutoff_time` in `cutoff_tz` (2.1 rule 1); identification is deterministic (scanline → loan number → coupon OCR via `lockbox.image_ocr`) and an identified item becomes a `payments` row (`channel = lockbox`, `instrument = check`, `idempotency_key` per the data model, `status = identified`) with 2.1's receipt set Dr `clearing_cash` / Cr `suspense_unapplied` posted on `received_on`; an unidentified item becomes 6.5's `suspense_items` row (`source = lockbox`) with the same receipt set and `lockbox.item.unidentified`. The batch emits `lockbox.batch.received` (arming 2.1's and 6.1's deposit clocks) and, once every item is a payment or a suspense item, `lockbox.batch.posted` (satisfying `SM_LOCKBOX_BATCH_POSTED_1BD`). The identified payments are posted by the loan's next `cashiering_daily` unit (rule 6) — the same day when the ingest runs before the planner's cashiering window, which the registry orders.
8. **ACH origination and returns as cycles.** `ach_file_build` (banking days, 14:00 ET): for every active `autodraft_enrollments` row whose next settlement date (2.3 rule 3: chosen day or due date, ≤ due + grace, preceding banking day when the gate would otherwise be breached) is T+1 or T+2, `nacha.build_entry` builds the entry for `amount` = P effective for the installment + `extra_principal_cents` (2.3 rule 4) — refused by `NACHA_WEB_ACCOUNT_VALIDATION_GATE` when unvalidated, held by `REGE_1005_10D_VARIABLE_AMOUNT_NOTICE_10` when the amount changed without a sent notice, rejected by `FNMA_C1103_DRAFT_BY_PENALTY_FREE_DATE_GATE` when the settlement date is past the penalty-free date — into one `ach_files` row per build (`file_id_modifier`, control totals, `hash`, the file stored through 35.2) transmitted through the `nacha` adapter; `ach.file.built` satisfies `SM_ACH_FILE_BUILD_1BD`. On settlement (`ach.entry.settled` from the adapter's settlement feed) each entry becomes a `payments` row (`channel = ach_debit_origin`, `received_on = settlement_date`, `status = received`) for the loan's next unit. `ach_returns_ingest` (banking days, 08:00 ET): the return/NOC file is stored (`ach_return_files`, unique `sha256`), each return matched to its `ach_entries` row by trace number and written as `ach_returns` with `ach.return.received{code}` (2.3's literal); `ach.return.action` then applies 2.3 rule 7 as one command per entry inside the loan's unit of work: R01/R09 → 2.1 `payment.reverse{reason: returned_item, return_code}` (the mirror set; the installment row `restored` to `due`), the NSF fee through 2.7 rule 7 (`nsfFee`: only when `loan_servicing_configs.nsf_fee_allowed`, `min(2,500¢, cap)`, once per item, never for R11 or bank error), 2.3's return notice, and a reinitiation entry with description "RETRY PYMT" and effective entry date = the third banking day after the return's settlement date (policy within 2.3's 3–5) unless the borrower has paid otherwise, the loan is on hold, or `NACHA_NSF_REINITIATION_180_MAX2` is exhausted (then `suspended_returns`, hand-off to `borrower-comms`); R02/R03/R04/R20 → the account terminated on the enrollment, no reinitiation; R05/R07/R10/R29 → enrollment cancelled, a fraud case (2.3); R11 → a corrected entry within `NACHA_R11_CORRECTED_REINITIATION_60`, no fee. `ach.return.actioned` satisfies `SM_ACH_RETURN_ACTIONED_1BD`. A return arriving after the loan's unit ran is actioned by the ingest itself (the command is loan-scoped and transactional); the next unit sees the restored row.
9. **Per-loan time zone, jurisdiction and servicer identity replace the constants.** `servicing_config.write` runs at `loan.boarded` in the boarding transaction: `time_zone` = the state's default from the reviewed map (`properties.state`, with county overrides for split-zone states; `time_zone_source = state_default`), `jurisdiction_state = properties.state`, `servicer_profile_id` = the active `servicer_profiles` row of the servicing party, `lockbox_id`, `channels_enabled`, `late_charge_terms` = 2.7 `lateChargeTerms(note, jurisdiction_rules.rules.late_charge)`, `nsf_fee_allowed` from `jurisdiction_rules.rules.nsf_fee`; `loan.servicing_config.written` satisfies `SM_LOAN_SERVICING_CONFIG_AT_BOARD_0`. Every loan-local civil date — the cashiering unit's `local_date` (rule 6), 2.7's 00:30 grace-end run, 11.1's 00:05 counter (35.9), 13.1's 120-day gate, the Reg X day count on the statement — is `wallClock(instant, config.time_zone).date` (src/kernel/calendar/zoned.ts:22); `LOAN_LOCAL_TZ` (delinquency.ts:27) is deleted and a read with no config row is a typed refusal (`CONFIG_REQUIRED`), never a default zone. Every servicing notice's servicer block (7.1 statements, 7.4, 4.x, 16.x, 11.x) is rendered from the loan's `servicer_profiles` row by `servicer_profile_id` as of the notice date; `SERVICER_CONTACT` (servicing.ts:46) becomes the FAKE build's seeded `servicer_profiles` version 1 with the same values, `status = active`, so no rendered text changes until `compliance` activates version 2 with the go-live values. Activating a profile version needs `compliance` and writes a decision; a profile change re-renders nothing retroactively (notices are stored bytes, 35.2).
10. **Nothing here decides a money figure.** The schedule is arithmetic on the note's terms; the unit dispatches 2.1, 2.7 and 2.3's own commands; a return applies 2.3's rule; a fee waiver, a lockbox variance resolution that changes an amount, or a reprojection touching a satisfied row is an `officer` command with a decision record, refused otherwise with nothing written.

#### AI agent design (AI-first)
`cashiering` agent (tools: `installments.write`, `installments.reproject`, `installments.read`, `cashiering.run_unit`, `lockbox.ingest`, `lockbox.item.resolve`, `ach.file.build`, `ach.returns.ingest`, `ach.return.action`, `servicing_config.write`, `servicer_profile.write`, `writeDecision`). End-to-end: unprompted, the agent writes the schedule inside every boarding transaction and re-projects it on every `loan_terms.activated` / `loan_terms.version.activated` / `loan_terms.versioned`; runs the loan's daily unit when 35.3 hands it the job, posting through 2.1, testing through 2.7 and checking through 2.3 with state it derived itself; ingests the lockbox file, identifies items and hands the rest to 6.5; builds and transmits the ACH file within 2.3's gates; ingests the return file and applies 2.3 rule 7 per entry. It proposes for a human: the resolution of a lockbox variance or an unmatched item (`ops_analyst`; `officer` when an amount changes), a reprojection that would touch a satisfied row (`officer`), any fee waiver (`officer`, 2.7 rule 5), an override of an automatic return action (`officer`), and every servicer-profile version and manual time-zone change (`compliance`). It never invents a payment, a fee or a rate; never edits a satisfied row; never posts against caller-supplied state; never defaults a time zone or a servicer block. Decision record schema: `{loan_id?, batch_id?, entry_id?, action, inputs: {terms_id | as_of_date | file_sha256 | return_code}, outputs: {rows | posted | fee_ids | reinitiation_entry_id | variance_cents}, rule_set_version: cashiering.schedule.v1 | cashiering.allocation.v1 | cashiering.returns.v1, model_version: deterministic, prompt_version: 35.5-v1, confidence: 1, rationale}`. Guardrails: `SCHEDULE_REQUIRED` (no `loans` row without its rows), `SATISFIED_ROW_FROZEN`, `NO_CLIENT_STATE`, `ONE_UNIT_PER_LOAN_PER_DAY`, `CONTROL_TOTAL_MATCH` (no posting from a batch in variance), `GATES_ARE_2_3S` (an entry refused by a 2.3 gate is never forced), `MAX_2_REINITIATIONS_180`, `NSF_ONLY_WHERE_ALLOWED`, `CONFIG_REQUIRED` (no loan-local date without a config row), `NO_MONEY_FIELD` (no tool here changes a money field outside the owning engine's command with the owning role). Escalations: `officer` for a schedule that cannot be written at boarding, a stale schedule after a terms change, a missed daily receipt, a lockbox variance, a batch unposted after one business day, a missed file build, an unactioned return; `compliance` for a loan without configuration and for every servicer-profile activation; `ops_analyst` for unmatched items and dead units (35.3).

#### Edge cases and failure modes
- A transfer tape with `next_due_date` earlier than the transfer date (delinquent at boarding) → rows from that due date, each `due`; 11.1's counter opens the windows on the first unit (35.9); the transfer-window shield (`misdirected_payments.protected`) is 2.7's, not the schedule's.
- A tape with no `pi_cents` for an ARM whose change date has passed → `SCHEDULE_REQUIRED` refuses the board with the missing field named; 1.1's exception, not a guessed payment.
- A loan whose first row is in the past at fund (a first payment date before the funding date — a data error) → refused at fund; the boarding validation names it.
- `loan_terms.activated` with `effective_from` before a satisfied row → the reprojection replaces only `due` rows on or after the effective date and records the earlier satisfied rows as `rows_kept`; if the source is a 4.1 correction that must restate a satisfied row, the correction reverses the payment first (2.1 rule 9) and re-posts.
- A curtailment between two rows (2.4) → the next unit posts interest on the actual UPB (rule 4), the row's `interest_cents` differs from the posted figure by the curtailment's month of interest, recorded on the unit; the schedule is re-projected only when 2.4 re-amortizes (Form 181).
- Two units for the same loan and day (a planner rerun, a demo advance) → the second finds the `done` row and completes with nothing written (`ONE_UNIT_PER_LOAN_PER_DAY`).
- The lockbox file arrives twice (same `sha256`) → the second ingest is a no-op with a decision naming the first batch; a different file for the same date is a second batch.
- An item's scanline names a paid-off or transferred-out loan → `unidentified` with `match_method = scanline` and the loan named; 6.5 refunds or forwards (17.x).
- Same-day duplicate debit built by our error → 2.3's reversal-entry rule (5 banking days, **[PARTIALLY VERIFIED]** by 2.3) and a refund credit; the payment is reversed; no NSF fee.
- A return on an entry the unit has not yet posted (return before settlement processing) → the entry goes `returned` with no reversal (`action: none_already_paid` is not used; the action is `reversed_reinitiated` with `payment_id` null and the payment row `returned` before any allocation).
- A NOC (`ach.noc.received`) → `ach_nocs` row, the enrollment's account fields corrected on the next build (2.3 rule 2 validation by warranty); no payment effect.
- A property in a split-zone county (e.g. AZ Navajo Nation observes DST) → the reviewed map's county override or a manual `time_zone_source = manual` row by `compliance`; the boarding never guesses.
- The active `servicer_profiles` row expires with no successor → notices refuse to render (`CONFIG_REQUIRED`) and `compliance` is escalated; nothing renders with a stale block.
- The demo clock advances three days → three planner passes, three `cashiering_daily` runs with `period_key` per day, each loan's unit once per day (35.3 rule 10), receipts per day.

### Open questions / decisions
1. Resolved: 35.3, 35.4 and this process all spell the daily receipt `cashiering.daily.run_completed` (the registry def's literal; 35.4 rule 1's `eod_cutoff` row waits on it). Nothing remains open here.
2. Should the schedule store rows for ARM periods after the next change date at all, given they are certain to be replaced? **Default: yes, at the current rate — the contract's payment until the change, so statements, payoff quotes and the counter have a row for every due date; `rate_bps` and `terms_id` make the projection visible.**
3. Should the daily unit be three cycles (posting, late charges, amount-change checks) as 35.3's open question 4 allows? **Default: one unit, three steps, one transaction per loan per day; the ACH build and the lockbox ingest are their own cycles because their cadence is per banking / servicer business day, not per loan.**
4. Should the lockbox-expected clock be per lockbox rather than global? **Default: global while there is one lockbox (the FAKE build and the first bank); a second lockbox gets a `subject: "lockbox:<id>"` override on the same code.**
5. Should the time-zone default come from the property's state or the borrower's stated residence for non-owner-occupied loans? **Default: the property's state for every loan (Reg X §1024.39's windows run against the mortgage; the borrower's zone governs 11.x's calling hours, `REGF_1006_6B1_QUIET_HOURS`, not this row).**
