### Blueprint row
Today the sweep runs its passes and counts the outbox (src/runtime/app.ts:246-300), the FAKE reviewers approve their six roles' items after a delay (src/infra/integrations/reviewers.ts:40, 78), and the console shows a queue of escalations, portal tasks, held notices, dead letters and breached timers (src/console/pg-store.ts:31-39) — but nobody watches whether a registered cycle ran at all, whether a dead message is an outage or a poison payload, or whether a FAKE approval happened where it never may. And the only statement of progress, `npm run audit`, measures spec units — T-titled tests, DDL (tools/audit.py:62), armable timers, bus tool strings (tools/audit.py:69), templates, figures — with no hosted dimension (docs/audit/COVERAGE.md:1-12): the only claims of hosted behaviour are the deploy smoke of `/healthz`, `/app`, `/` and `/ops` (.github/workflows/deploy.yml:315-357) and the twelve-outcome browser walk (.github/workflows/walk.yml:3), and the single-process lifecycle journeys skip wherever Postgres is absent (src/runtime/lifecycle.test.ts:37-40; src/runtime/purchase-lifecycle.test.ts:49). This process is two things with one owner: the ops steward — an agent pass over 35.3's runs and registry, 35.1's outbox and sweep runs, the breach escalations and the FAKE reviewers, producing one hashed daily ops report per environment and opening the exceptions a person must see; and the audit's two execution columns — `hosted` (every tool executed or typed-refused through the hosted API against the probe's own database) and `persisted` (row counts per spec table after the journeys, beyond the post-migrate count) — kept in a separate `exec_totals` baseline key so "built" can no longer be claimed without "runs on the hosted runtime".

### Verified requirement (as of 2026-09-15)
**Monitoring and the kill switch (18.1 rule 5; src/domain/qc-audit/findings.ts:36-41; src/app/agents.ts:61-68).** `ai_monitoring_metrics` (db/migrations/0021_qc_audit.sql:174-190) holds daily rollups per system — decision volume, escalation rate, override rate, low-confidence rate, tool-error rate — and the human override rate of a T1 system has a target band of 2–15%: two consecutive days outside it trip the kill switch (`killSwitch` returns true when both of the last two daily rates are `< 0.02` or `> 0.15`; `AgentRegistry.recordOverrideRate` sets the agent AI-off with the two rates in its reason). Nothing on the runtime writes `ai_monitoring_metrics` or calls `recordOverrideRate` today; the daily ops report is the feed.

**A timer breach is a person's finding (reviewers.ts:174; app.ts:270-291).** The breach pass opens one escalation per breach to the registry's first escalation role, and the FAKE reviewers leave `sev1`–`sev4` escalations open by rule ("never auto-closed"). The steward inherits that rule verbatim: it opens, classifies, assigns and reports; it completes nothing a clock opened.

**The outbox requeue is a person's act, capped at three (34.4 rule 2–3; src/runtime/controls/outbox.ts:70-86).** `controls.outbox.requeue` refuses an agent actor (`ROLE_REQUIRED`) and a fourth hand requeue (`REQUEUE_CAP_3`, one `ops_analyst` escalation per message); each requeue is the event `outbox.requeued{message_id, adapter, from_status, requeue_no, cap, by, by_role, reason}`. The steward's one automatic requeue after an adapter recovers is a distinct, bounded act (rule 4 below) and is never counted as a hand requeue.

**The sweep drains the outbox and records itself (35.1 rules 11–12).** `outbox.dispatch` runs `OutboxDispatcher` with `DEFAULT_RETRY` (5 attempts, 60 s base, 30 min cap), writes `outbox_dispatches` per attempt and emits `integration.message.sent` or `integration.message.dead{message_id, adapter, attempts, error, dead_at}`; each firing writes a `sweep_runs` row and `sweep.run_completed` or `sweep.run_skipped`. Until 35.1 lands, `PgOutbox` is exported and never constructed in runtime code (src/infra/integrations/pg-outbox.ts:18) and the sweep only counts the backlog (app.ts:298) — the steward's exception feed is empty, not wrong.

**A never-run cycle is a registry finding, not a clock (35.3 rule 11).** The engine arms only on a trigger event (src/kernel/timers/engine.ts:161-181), so a cycle that has emitted nothing cannot be named by a timer; 35.3's planner sets `cycle_registry.next_expected_by` from `expected_by_rule` and `overdue_since` when it passes without a receipt, and "35.11's steward opens the escalation and owns the follow-up".

**The FAKE reviewers exist only outside production (35.7; reviewers.ts:40-46; src/runtime/config.ts `loadConfig`).** `FAKE_REVIEWER_ROLES` are filled when `INTEGRATIONS=fake` and `FAKE_REVIEWERS` is not `off`; every row they write carries the actor `{human, "FAKE:<role>", role}`; `ENVIRONMENT` is `nonprod` unless set. A `FAKE:` actor on a production day is a control failure, whatever the switch says.

**The audit's units and ratchet (tools/audit.py:62, 69, 113-121; docs/audit/baseline.json).** `created` is the set of names in `CREATE TABLE|VIEW` statements — DDL, not use; `bus_tools` is the set of `(process, name)` pairs `ALL_TOOLS` registers — registration, not execution; `check()` iterates `b['totals']` and `b['done']` only, so a new key beside them is invisible to the existing ratchet until `check()` is taught it. Every tool already executes with an empty input through the in-memory bus without a `TypeError` (src/app/tools.test.ts:99-105); the hosted probe is that contract over HTTP against Postgres, where `service()` misses answer 501 `not_wired` (src/app/tools.ts:85 → src/runtime/server.ts:385).

**The timer offset grammar accepts hours (src/kernel/timers/offset.ts:18, 91; engine.ts:84-85)** — `+1 hours` and `+2 hours` parse and are evaluated on the anchor instant, not a civil date; the template's list names only day units, so the rows below cite this. Verified by running `parseOffset` on every offset in this file's timer table (`+1 hours` → `{kind: step, n: 1, unit: hours}`; `+1 calendar_days, 00:15 ET` carries the ET wall time); `tools/spec_lint_names.py` checks only `business_days_*` units against the kernel's `DAY_UNITS` (:57, :71), so an hour row passes it; 35.3 and 35.8 rely on the same unit.

**CI's Postgres does not host the journeys' database (.github/workflows/ci.yml:10-14, 23-24; lifecycle.test.ts:37).** The service database is `supermortgage`; the journeys default to `supermortgage_test` and skip when it is unreachable, so `npm test` in CI proves the unit harnesses and the audit ratchet, not a Postgres-backed journey. **[PARTIALLY VERIFIED — that the service's `sm` user may `CREATE DATABASE supermortgage_test` on the runner is assumed from the Postgres image's superuser default and is confirmed by the first CI run of this process, not before.]**

**Discrepancies vs blueprint**: (1) The §35 plan (d1238cc) split this into 35.5 "hosted and persisted measurement" and 35.6 "operations stewardship" under an `ops-steward` agent; at HEAD 35.3 owns `ops-steward` for the cycle engine, so this process's owner is `qc-audit` — the agent that already owns 18.1's monitoring and 18.2's evidence — and "the ops steward" is what its pass is called. (2) The plan's requeue "delegates to 34.4 with the cap inherited"; 34.4's guard refuses an agent actor, so the automatic requeue is this process's own bounded act (once per message, after an adapter recovery or on a high-confidence transient) and the hand requeue stays 34.4's. (3) The plan's `SM_ADAPTER_DOWN_1H` becomes `SM_OPS_ADAPTER_DOWN_1H` and gains a sibling for missed cycles; the plan measured `hosted` expecting only 1.1 to move (5 → 11 of its tools) — at HEAD `orig-boarding` (30.2) and `tolerance-21-5` (25.1/25.2's delegation) also answer 501, so three service keys are the probe's expected finding until 35.1's hydrating adapters land. (4) The plan's `hosted` was measured in CI only; a deployed environment drifts from CI (instances, secrets, the demo clock), so `audit.hosted.run` also runs against the deployed API under a principal (35.7) and `SM_HOSTED_PROBE_WEEKLY` keeps it current. (5) The walk has twelve outcomes at HEAD (walk.yml:3), not eleven.

#### State machine
Per exception (`ops_exceptions.status`): `open` —(`ops.exceptions.classify`; the classifier ran)→ `triaged`; `triaged` —(`ops.exceptions.assign` by the agent when `kind ∈ {needs_person, poison}` or by an `ops_analyst`)→ `assigned`; `open | triaged | assigned` —(the source resolved: `integration.message.sent` for the message, `cycle.run.completed` for the cycle or run, `job.unit.resolved` for the unit, `escalation.completed` for the escalation, `role.staffed` for the role; or `ops.exceptions.resolve{resolved}` by an `ops_analyst`)→ `resolved`; `triaged | assigned` —(`ops.exceptions.resolve{abandoned, reason}` by an `ops_analyst`)→ `abandoned`. Terminal: `resolved`, `abandoned`. The agent performs `open → triaged`, `triaged → assigned` and the source-driven `→ resolved`; a person performs every `abandoned` and every hand `resolved`. Per report: `produced` (append-only). Per probe run and per measurement run: `started → completed | failed` (a failed run writes its row with `results` so far and emits nothing; the audit treats it as not measured).

#### Business rules and calculations
1. **The steward reads, opens, classifies, assigns and reports; it completes nothing a clock or a section opened.** Its pass runs after 35.3's executor inside the sweep's lease (35.1 rule 12) under the actor `{agent, qc-audit}`; every state change it makes is an `ops_exceptions` row, an `exception_triages` row, an `agent_decisions` row and an event. It never calls an escalation completion, never writes a section's table, never satisfies, extends or cancels a timer (34.4 rule 1), and never changes a money field (rule 9). Guardrail `NEVER_COMPLETES_A_BREACH` (reviewers.ts:174's rule, now the agent's).
2. **A missed cycle is detected from the registry, not a clock.** `ops.cycles.watch` reads `cycle_registry` rows whose `next_expected_by` is before `as_of` and whose latest `cycle_receipts` row is older than the period the rule names (35.3 rule 11 sets `overdue_since`); for each it opens one exception `{source_kind: cycle_registry, source_id: "<cycle_code>:<period_key>", kind: missed_cycle}`, emits `ops.cycle.missed` with `consecutive_misses` = the number of consecutive period keys without a receipt, and opens one `ops_analyst` escalation (`sev2`, payload `{cycle_code, period_key, next_expected_by, owner_process, owner_agent, runbook}`); a second pass over the same `(cycle_code, period_key)` adds nothing (the live-exception index). When the receipt arrives, `ops.cycle.recovered` resolves the exception and satisfies the clock; the escalation stays open for the person (rule 1). A stalled run (`SM_CYCLE_RUN_STALLED_1D` breached) and a dead unit (`job.unit.dead`) open exceptions of kinds `stalled_run` and `dead_unit` the same way, resolved by `cycle.run.completed` and `job.unit.resolved`.
3. **Classification is deterministic and its signals are stored.** Rule set `ops.v1`, no model. For a dead message the classifier counts, per adapter, over `outbox_dispatches` and `integration_messages`: `D15` = dead or retry outcomes in the last 15 minutes, `S60` = successful sends in the last 60 minutes, `A` = the message's `attempts`, `C` = its last `failure_kind`. Then: `adapter_down` when `D15 ≥ 3` and `S60 = 0` (confidence `0.95`); `transient` when `C ∈ {timeout, connection_reset, http_5xx, rate_limited}` and `S60 ≥ 1` (confidence `0.90` when `S60 ≥ 3`, else `0.80`); `poison` when `C ∈ {validation, http_4xx, schema}` and `A ≥ 5` (confidence `0.95`); otherwise `needs_person` (confidence `0.50`). The `signals` column holds `{D15, S60, A, C}`; the decision record's `confidence` is the number above. The classifier runs at most once per exception automatically and again on demand; each run is a triage row.
4. **The automatic requeue is bounded to one per message and needs confidence ≥ 0.85.** `ops.exceptions.requeue{op: auto}` runs only for `kind = transient` with confidence `≥ 0.85`, or for `kind = adapter_down` once the adapter has a success after `classified_at` (the outage ended); it sets `integration_messages.status = queued` with `attempts = 0` inside the sweep's transaction, appends 34.4's literal `outbox.requeued{…, by: "agent:qc-audit", by_role: null, auto: true, reason}` and increments `ops_exceptions.auto_requeues`; a second automatic requeue of the same message is refused `AUTO_REQUEUE_CAP_1` and the exception is assigned to `ops_analyst` instead. The automatic requeue is not a hand requeue: 34.4's `REQUEUE_CAP_3` counts only rows with a human `by`. `transient` below `0.85`, `poison` and `needs_person` are never requeued by the agent — `ops.exceptions.requeue{op: propose}` writes a `requeue_proposed` triage row and the assignment; the person's requeue is 34.4's route with the session's actor.
5. **The daily report is one hashed row per environment-day, idempotent by content.** `ops.report` assembles, for `(environment, as_of_date)` in America/New_York, every column of `ops_daily_reports` from the tables and events listed under Data model (counts and codes only), computes `sha256` over the canonical JSON, and appends a row only when no row for the day carries that hash; `ops.report.run_completed{changed: true | false}` is emitted on every run (the clock needs the day's receipt even when nothing changed). `produced_by` is the sweep run or the person who forced it. The report is rendered by 35.2 into one document and is included in 34.4's evidence pack for a period. The first run of a day happens on the first sweep at or after 00:15 ET (the previous day's report, so the day's last sweep is in it); the demo clock's crossing of a day counts as that.
6. **The report feeds 18.1's monitoring.** For every `ai_systems.code` that is a bus agent the report computes, over the day's `agent_decisions`: `decisions` = rows by that agent; `overrides` = rows whose `approved_by` is a human who chose a different disposition than the agent proposed (the decision's `action` ends in `_rejected` or the escalation completion's `disposition` differs from the proposal) plus 35.8's `work.action.decided{decision: rejected}` rows for the agent; `override_rate = overrides ÷ decisions` (decimal, precision 20, four places, half-up — the column is `numeric(6,4)`), `escalation_rate = escalations opened by the agent ÷ decisions`; it upserts `ai_monitoring_metrics(system_code, day)` and calls `AgentRegistry.recordOverrideRate(agent, day, override_rate)` (agents.ts:61-68) for T1 systems. Worked figures: day 1 — 61 overrides over 340 decisions = 0.17941… → `0.1794` (out of band: > 0.15); day 2 — 52 over 310 = 0.16774… → `0.1677` (out of band) → two consecutive days out of band → `killSwitch` returns true (findings.ts:36-41), the agent is AI-off with the reason naming `17.9%, 16.8%` and `ai.kill_switch.tripped{system_code, metric: override_rate}` is emitted (ops-18-1.ts:464-470); a day 1 of 48 over 400 = `0.1200` followed by day 2 `0.1677` is one day out of band and trips nothing. A day with zero decisions writes `decision_volume = 0` and a null rate, and a null day never counts toward the two.
7. **A FAKE actor in production is a sev-1 control failure.** `fake_approvals` = the day's `agent_decisions` and `loan_events` rows whose actor id starts with `FAKE:` (reviewers.ts:78); `fake_roles` the distinct roles. Outside production it is reported and nothing more. Under `ENVIRONMENT = production` a count above zero emits `ops.fake_in_production{environment, as_of_date, roles, count}`, opens one exception `{source_kind: fake_actor, source_id: "<as_of_date>", kind: fake_in_production}` and one `sev1` escalation to `compliance` — once per day, however many rows.
8. **The runbook is generated from the registry.** `ops.runbook.read{timer_code}` returns `{code, kind, trigger, anchor, offset, satisfied, breach_text, owner_role, severity, spec_path, process, section}` from `spec/registry/timers.json` and `spec/registry/manifest.json`; `{cycle_code}` the `cycle_registry` row with its owner and `expected_by_rule`; `{adapter}` the adapter's retry policy, its last success and its open exceptions. An unknown code is refused `UNKNOWN_CODE`. Nothing in the runbook is authored by hand or a model.
9. **Nothing here changes a money field.** The tools' inputs are ids, codes, dispositions and reasons; an input with a money-shaped key (34.4's `NO_MONEY_FIELD` pattern: `_cents`, `_bps`, `_pct`, `amount`, `waive`, `refund`, `entry_set`, `post`, …) is refused before any read. A waiver, a reversal and a posting remain the owning section's `officer` commands.
10. **The hosted column.** `tools/hosted-probe.ts` (`npm run test:hosted`) drops and creates `supermortgage_probe` (`PROBE_DATABASE_URL`; the purchase journey's own-database pattern, purchase-lifecycle.test.ts:49), migrates it with `db/migrate.sh`, boots `Runtime` + `createApiServer` on it with a FAKE port set and `ENVIRONMENT = probe`, seeds one loan through `POST /v1/transfers/batches` and one application through `POST /v1/applications`, and for every `ALL_TOOLS` pair posts `{}` to `POST /v1/loans/{loan}/tools/{process}/{name}` (sections 1–19, 32–35) or `POST /v1/applications/{app}/tools/{process}/{name}` (20–31) as the tool's own agent under a service principal (35.7). Status per pair: `executed` (2xx), `refused_typed` (a 4xx whose body carries the bus's typed `code` — `CommandRefused`, `RoleDenied`, a guard — which the unit of work rolled back, so nothing was written), `not_wired` (501, `PortUnavailable`), `errored` (500, or a 400 whose reason is a `TypeError`/`RangeError`/`SyntaxError` message). The run writes `hosted_probe_runs` in the probe database and `docs/audit/hosted.json = {run_id, target, database_name, migration_head, git_sha, as_of_date, results: [{process, name, status, code}]}`. `target: deployed` runs the same list against the deployed API's origin with the environment's probe loan and application (seeded by `seed-demo`), never against production.
11. **The persisted column.** `audit.persisted.count` records, on `supermortgage_test`, `count(*)` per spec table immediately after `db/migrate.sh` (the post-migrate baseline — seeded rows such as `notice_templates` and `ai_systems` are in it) and again after the journey files have run under the journey lock (src/infra/db/test-lock.ts:12); `delta = after − post_migrate`; verdict `persisted` when `delta > 0`, `seeded_only` when `delta = 0` and `post_migrate > 0`, `untouched` when both are 0, `missing_ddl` when the table is in the manifest and not in the database. `expected` is true when a §35 journey step names the table in its `writes` list (35.5, 35.6, 35.9, 35.10 and the two lifecycle tests declare theirs); `sections_complete` lists every section all of whose expected tables are `persisted` and whose `projection_gaps` count for the run is 0. Probe rows never enter the count (the probe has its own database). Output `docs/audit/persisted.json` and the two tables.
12. **The audit reports the columns and ratchets them separately.** `tools/audit.py` gains `EXEC_UNITS = ('hosted', 'persisted')`: per process, `hosted = executed + refused_typed` over `tools` (the manifest's tool list; a process with no tools is `0/0`), `persisted = tables with verdict persisted` over `tables`; two columns on the COVERAGE.md process rows (after `figures`, before `units`) and two totals lines; `docs/audit/baseline.json` gains `exec_totals: {hosted: {spec, built}, persisted: {spec, built}}` and `exec_done: [pid…]` beside — never inside — `totals` and `done` (check() iterates `b['totals']` at :117 and `b['done']` at :120 and is extended, not reinterpreted). The columns are measured only when `docs/audit/hosted.json` and `docs/audit/persisted.json` exist and their `migration_head` equals the newest file under `db/migrations`; otherwise the brief prints `hosted: not measured (stale: <head> vs <newest>)` and `--check` compares nothing exec — a stale probe never fails the build, it only stops the claim. With current files, `--check` fails when either exec total falls below `exec_totals` or a process in `exec_done` is below `hosted = tools` and `persisted = tables`. `--baseline` writes both keys. The per-process `done` rule and `UNITS` are unchanged; the six spec units are still what "built" counts — the exec columns are what "runs" counts, and COMPLETION claims in docs quote both.
13. **The three known 501s are findings, not failures.** At HEAD the service keys `boarding` (1.1), `orig-boarding` (30.2) and `tolerance-21-5` (25.1/25.2) are the only `service()` misses (src/app/tools.ts:85); the first probe records them as `not_wired` per tool, `exec_totals.hosted.built` is set from that run, and 35.1's hydrating adapters move them — the ratchet then moves up in the same commit.

No money figure is computed here.

#### AI agent design (AI-first)
`qc-audit` agent, running as the ops steward (tools: `ops.cycles.watch`, `ops.exceptions.list`, `ops.exceptions.classify`, `ops.exceptions.requeue`, `ops.exceptions.assign`, `ops.exceptions.resolve`, `ops.report`, `ops.runbook.read`, `audit.hosted.run`, `audit.hosted.report`, `audit.persisted.count`, `writeDecision`). End-to-end: unprompted, every sweep and every demo step, the agent watches the registry for missed and stalled cycles and dead units, opens exceptions for them and for every dead message, unstaffed role and FAKE actor, classifies each with the deterministic rule set, requeues at most once where the rules allow, assigns the rest to `ops_analyst`, resolves exceptions whose source recovered, and produces the day's report and the 18.1 metrics; in CI and weekly it runs the hosted probe and the persisted count and writes the audit files. It proposes for a person: every requeue below the confidence line or beyond the automatic cap, every `poison` and `needs_person` exception, every abandonment. It never completes an escalation, never satisfies or edits a clock, never runs a section's command, never touches a money field, never writes a payload or a name into an exception, and never trips or resets a kill switch itself (the override-rate trip is 18.1's own rule through `recordOverrideRate`; the hand switch is 34.4's two people). Decision record schema `{exception_id | report_id | run_id, action, kind?, confidence, signals?, rule_set_version: ops.v1 | audit.v1, model_version: deterministic, prompt_version: 35.11-v1, rationale}` — `confidence` is rule 3's number for a classification and `1` for everything else. Guardrails: `NEVER_COMPLETES_A_BREACH`, `NO_CLOCK_EDIT`, `AUTO_REQUEUE_CAP_1`, `CONFIDENCE_FLOOR_0_85`, `NO_MONEY_FIELD`, `NO_PAYLOAD_IN_EXCEPTION`, `REPORT_IS_COUNTS` (nothing summarized by a model in the report), `PROBE_NEVER_PRODUCTION`, `EXEC_KEYS_SEPARATE` (the exec columns never alter `totals` or `done`). Escalations: `ops_analyst` for a missed cycle, an adapter down past an hour, an untriaged exception, a dead unit; `compliance` for a second consecutive missed cycle, a FAKE actor in production, a day without an ops report; `qc_officer` for a stale hosted probe; `ciso` when the report's `documents.integrity_findings` is above zero (35.2's own sev-1 is the primary; this is the report's cross-check).

#### Edge cases and failure modes
- 35.1 or 35.3 not yet landed (no `sweep_runs`, no `cycle_registry`) → the steward's pass reports `feeds: absent` per feed, opens nothing, and the report row carries nulls for those columns; the report clock still runs.
- The same message dies again after its one automatic requeue → a new `integration.message.dead` on the same `source_id` finds the live exception (`assigned`), adds a triage row `escalated` and does not requeue; a person's hand requeue via 34.4 is the only path.
- An adapter classified down recovers and the outage recurs within the hour → the exception resolved on the first success; the recurrence opens a new exception with a new one-hour clock; the report shows both.
- The demo clock advances 30 days in one request → thirty report rows in order, each `as_of_date` from the persisted offset, never `clock.now()` read twice; `SM_OPS_REPORT_DAILY` satisfied per day inside the step.
- Two sweeps in one minute → the lease (35.1) leaves one steward pass; the skipped firing writes nothing of this process.
- `ENVIRONMENT` unset on a job → `nonprod` (config.ts), never `production`: a FAKE actor is reported, not escalated; 35.12 makes the variable mandatory.
- The probe's seed loan or application refuses to board → the run is `failed` with the reason, `hosted.json` is not written, the audit says not measured; the ratchet stays green.
- A tool executes against the probe and writes an event that arms a timer → the probe database is dropped at the next run; probe rows never enter `persisted`.
- `hosted.json` older than the newest migration (a migration landed without a probe) → "not measured (stale)"; `SM_HOSTED_PROBE_WEEKLY` is unaffected (it counts days, not migrations).
- The deployed target's API is unreachable → the run is `failed{unreachable}`, one `sev3` escalation to `qc_officer`; the last good run stands with its date.
- A report re-run with `force` and unchanged content → no new row; `ops.report.run_completed{changed: false}`; the decision record says so.

### Open questions / decisions
1. Should the automatic requeue exist at all, or should every dead message wait for a person? **Default: one automatic requeue per message under rule 4's conditions; a person after that. A dead message is by definition one that failed five times, so the automatic act is a recovery after a classified outage or a high-confidence transient, not a retry loop.**
2. Is `refused_typed` enough for "hosted", or must a process's tools execute with a real input? **Default: `refused_typed` counts (the contract of src/app/tools.test.ts:99), and `persisted` is where real inputs are proved — a process is in `exec_done` only when both columns are full.**
