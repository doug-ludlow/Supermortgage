### Blueprint row
The console today lists escalations, portal tasks, held notices, dead letters and breached timers and lets a signed-in person complete an escalation, requeue a message or read a loan's events, balances, timers, decisions and notices (src/console/pg-store.ts:54-62 — a read-only projection). A generic role-gated bus route exists — `POST /ops/api/tools/{process}/{name}` (src/console/server.ts:30; the bus block at :431-450 with the tool's role gate at :446-450, the role chosen at :274 by `chooseRole`) — but nothing in the UI calls it (`grep 'api/tools' src/console/ui/index.html` = 0 at HEAD; the views 34.5's `NAV` declares — index.html:68-74, `VIEWS` — are `home`, `people`, `loans`, `book`, `dashboard`, `controls`, `agents`, `ai`, `staff`, `access_review` and their record sub-views `directory` / `directory_account`, `loan`, `book_import` / `book_loan`, `controls_clock` / `controls_pack`, `ai_party`: no `work` view), so a person can act on a loan only by POSTing spec-shaped JSON whose inputs must carry engine state: 2.1 `payments.read/write{op: post}` wants the whole `LoanCashState` and the custodial ids (src/runtime/servicing.ts:140 passes `state: facts.state, custodial: facts.custodial` from the caller); 26.3 `requestWarehouseAdvance` wants `conditions`, `rescission`, `ptf` and `cash_to_close` (src/runtime/lifecycle.test.ts:587-592 hand-builds them); 16.2 `postPayoff` wants the bucket cents (lifecycle.test.ts:798-799). This process is the missing work surface: eleven screens — review and approve an LE, review a CD, clear underwriting conditions, schedule a closing, release funding, post a payment, reverse a payment, run an escrow analysis, quote a payoff, decide a loss-mitigation request, work a foreclosure case, work a bankruptcy case — each a read projection plus named actions, each action a call to the owning section's bus tool with every engine input derived server-side from the typed record (35.1), the installment schedule (35.5) and the orchestration (35.6), with a queue of the work that needs a person and one action-log row per act (34.1 rule 4). A person supplies a decision; the platform supplies the state.

### Verified requirement (as of 2026-09-15)
**One service path (ARCHITECTURE §7; 34.1 rule 3).** "`service.ts` is the only way to change state; the ops console and the agent both call it." The staff session resolves to `{kind: human, id: staff_user_id, role}` for the route's chosen role when the user holds it (src/console/server.ts:5-15, :265-274; src/runtime/staff/roles.ts:70 `chooseRole`): on an act the role is the one the request names (`x-staff-role` / body `role`), refused 403 `ROLE_REQUIRED{role, held, act_as: [the accepted roles the account holds]}` when the tool does not accept it — never a silent substitution of a greater held role (34.1 rule 3 as amended 2026-09-15); a route that needs a role the user lacks answers 403 `ROLE_REQUIRED{role}` before any read; the `staff_actions` row records the role that acted (34.1 rule 4, `staff_actions.role`, migration 0139). Every screen action therefore *is* a bus command: the tool's own validators, guardrails, `moneyFields` and `humanRoles` (src/app/tools.ts:93-114) run unchanged; the screen adds no second path.

**The engine's inputs are the record's, not the caller's (35.1 rule 9; 35.3 / 35.5 / 35.6 `NO_CLIENT_STATE`).** 35.1 rebuilds every stateful service from the record before each command; 35.5 derives the 2.x cash state from `loan_installments` and the ledger and refuses a client-supplied one; 35.6 derives 26.3's `conditions`, `rescission`, `ptf` and `cash_to_close` inside its pass. A screen inherits the rule: the person's payload is a *decision* (ids, a disposition, a date choice, a reason, a figure only where the person is its source — the amount on a cheque, an approved annual disbursement), and any field the deriver owns is refused `NO_CLIENT_STATE` before any write.

**The action log (34.1 rule 4; 18.2).** One `staff_actions` row per portal request — route, method, subject ids, the bus command when one ran, the result and the refusal code, and the role that acted (`staff_actions.role`, migration 0139 — on a refusal the role asked for), ids only otherwise. Here every act also keeps the derived input as a stored artifact with a hash (35.2), so an examiner sees what the engine saw, and the decision record names the person, the screen and its version.

**Money fields and legal acts stay with the roles the sections name (ARCHITECTURE §6; src/app/roles.ts).** A payment reversal, a trustee-payment application, a payoff figure override, a fee waiver are `officer` acts (`assertNoAgentMoneyChange`, `requireOfficer`); a wire release is `funding_approver` under dual control (26.3); a condition clearance and the clear-to-close are `underwriting_reviewer` (23.3); LE approval is `mlo_of_record` (src/runtime/origination.ts:404); a loss-mitigation denial needs `lossmit_reviewer` (12.2, `SM_LM_REVIEWER_DENIAL_APPROVAL_2BD`); an attorney instruction is sent to, never by, `attorney`. Under 34.1 the staff portal holds four roles (src/runtime/staff/roles.ts:15); 35.7 adds `staff_users.reviewer_roles` so a person can hold `underwriting_reviewer`, `funding_approver`, `mlo_of_record`, `qc_officer`, `signing_officer` or `human_agent` on a staff session. **[PARTIALLY VERIFIED — 35.7 is authored in this section and not yet in the tree; until it lands the screens that need a reviewer role are visible and refuse `ROLE_REQUIRED`.]**

**Discrepancies vs blueprint**: (1) The blueprint imagines "screens" as UI; here a screen is a bus-addressable pair — `work.screen.read{code, subject}` and `work.screen.act{code, action, subject, decision}` — and the HTML is a thin client of those two tools, so a screen is testable against Postgres without a browser. (2) The console's queue (src/console/pg-store.ts:85-89, five kinds by role) is kept and extended, not replaced: 35.3's dead units, 35.6's held steps and 35.9's case milestones become items of the same queue with a `screen_code` that opens the right screen. (3) 2.1's own contract passes `state` in the input (servicing.ts:140); the screen never lets a person set it — the deriver fills it from 35.5 and the field is refused when present in the decision payload, which is exactly what 35.5's `cashiering.run_unit` does for the sweep. (4) Funding release goes through 35.6's `orchestration.release` / 26.3 `prepareWire{op: release}`, never a direct `requestWarehouseAdvance` with hand-built gates.

### Build spec
#### Inputs and triggers
- `GET /ops/api/work/queue?role=&screen=&subject=&status=` → `work.queue` (the console's five item kinds — escalation, portal_task, held_notice, dead_letter, breached_timer — plus `job_dead` (35.3 `job.unit.dead`), `orchestration_held` (35.6 `orchestration.held`), `approval_pending` (this process), `case_milestone` (35.9); each row carries `screen_code`, `subject_kind`, `subject_id`, `required_role`, `opened_at`, `due_at`).
- `POST /ops/api/work/items/{id}/claim` → `work.item.claim`; `POST …/release` → `work.item.release`; `POST …/close {disposition, reason, evidence_document_id?}` → `work.item.close`.
- `GET /ops/api/work/screens/{code}/{subject_kind}/{subject_id}` → `work.screen.read` (the projection and the list of actions the session may take, each with its decision-payload schema and the role it needs).
- `POST /ops/api/work/screens/{code}/{subject_kind}/{subject_id}/derive {action}` → `work.screen.derive` (dry run: the derived input, its hash and sources, no write).
- `POST /ops/api/work/screens/{code}/{subject_kind}/{subject_id}/act {action, decision, work_item_id?}` → `work.screen.act` (derive, dispatch, log — one transaction); for a money-field action the same route runs `work.action.propose` when the session lacks `officer`, and `POST /ops/api/work/actions/{id}/decide {decision ∈ {approved, declined}, reason}` → `work.action.decide` (a distinct `officer`).
- Events consumed to open items: `escalation.created` (the kernel's EscalationService, src/app/escalations.ts:33 — the literal the sweep's breach pass produces), `human_portal_task.created` / `human_portal_task.opened` (src/app/tools/section02.ts:179, section15-1.ts:163), `notice.held`, `integration.message.dead`, `timer.breached` (the console's kinds); `job.unit.dead` (35.3), `orchestration.held` (35.6), `work.action.proposed` (own), `case.milestone.due` (35.9).
- Schedules: `work.log.recon{as_of_date}` from the sweep once a calendar day (35.3 cycle registry row `work_log_recon`, daily); the claim-lapse breach handler.
- A person may start: any screen on any subject they may read (34.2 masking applies); a `manual` item (`work.item.open{screen_code, subject}`) for work no event raised.

#### State machine
Per item (`work_items.status`): `open` —(`work.item.claim`; the session holds `required_role`)→ `claimed` —(`work.item.release`, or `SM_WORK_ITEM_CLAIM_4H` breach)→ `open`; `claimed` —(`work.screen.act` on a money-field action without `officer`)→ `waiting_approval` —(`work.action.decide{approved}`; executes)→ `closed` | —(`declined`)→ `claimed`; `claimed` | `open` —(`work.item.close{disposition}`; or the source's own closing event: `escalation.completed` (src/app/escalations.ts:49), `human_portal_task.completed`, `job.unit.resolved`, `orchestration.released`, `timer.satisfied`)→ `closed`; any —(the source cancelled: 35.3's `cycle.run.cancelled` or a `job_events{kind: skipped}` row for the item's job — the kernel has no escalation-cancel event, an escalation ends only by `escalation.completed`; or `ops_analyst` `work.item.cancel{reason}`)→ `cancelled`. Terminal: `closed`, `cancelled`. Per action (`work_actions.status`): `proposed` —(officer)→ `approved` (a new `executed` row is written and linked by `approval_of`) | `declined`; `proposed` —(`SM_WORK_APPROVAL_1BD` breach, then a further 1 business day unattended)→ `expired`; a non-money action is written once as `executed`, `refused` or `error`. Who: any transition on an item by the person holding its role; `decide` only by a distinct `officer`; `cancel` by `ops_analyst`; the `case` agent opens items and proposes, never claims, closes or decides.

#### Timers and gates
| Timer code | Kind | Trigger event | Anchor | Offset & unit | Satisfied by | Breach action |
|---|---|---|---|---|---|---|
| `SM_WORK_ITEM_CLAIM_4H` | deadline | `work.item.claimed` | `claimed_at` | +4 hours | `work.item.released` | the claim lapses (`work.item.claim_expired`, `claim_lapses + 1`, status back to `open`); sev 3 → `ops_analyst` on the third lapse of one item |

`SM_WORK_LOG_RECON_DAILY` is a recurring global clock: it takes a cited `subject: "global"` override in `src/domain/operations-runtime/timers-35-8.ts` on the `timers-33-2.ts` precedent (armed on the global subject by the first run, re-armed by each `work.log.recon.run_completed`). `SM_WORK_ITEM_CLAIM_4H`'s `+4 hours` parses through the engine's hour unit (src/kernel/timers/offset.ts:18, engine.ts:84); its breach action (release the claim) is executed by the breach handler in `timers-35-8.ts`, the only place a breach does more than open an escalation, cited to this row.

Jurisdiction overrides: none of its own — every act carries the owning section's `jurisdiction_rules.*` through the tool it dispatches.

#### Business rules and calculations
1. **A screen is two tools.** `work.screen.read{code, subject}` returns the projection (the owning section's read tools run with the session actor — `installments.read` and the ledger balances for a loan, 23.3's condition list for an application, 16.1's last quote, 12.2's evaluation, 13.x/14.x case rows, the timers and escalations on the subject, the last ten `work_actions`) and the action list — each action with `code`, `process`, `tool`, the roles it needs (from the tool's `humanRoles`, never restated here), `money` (from `moneyFields`), its `decision_schema` and `derived_fields`. `work.screen.act{code, action, subject, decision}` derives, dispatches and logs in one unit of work under 35.1's per-loan lease; the HTML at `/ops` (view `work` — 34.5's Operations area and its application and loan pages are the shells it fills and list the screen codes; whether a screen is available is this process's T-ids' business, never 34.5's) calls nothing else.
2. **The person supplies a decision; the deriver supplies the state (`NO_CLIENT_STATE`).** Each action names its `derived_fields`; a decision payload that contains any of them, or any field not in its `decision_schema`, is refused `NO_CLIENT_STATE{field}` before the deriver runs and before any write. The derivers (`src/domain/operations-runtime/derivers-35-8.ts`, one exported function per action, pure over the rows they read, versioned):
   - `payment_post.post`: `state` = 35.5's derived `LoanCashState` (the same function `cashiering.run_unit` uses — servicing.ts:67's `loanCashState` moved behind 35.5), `custodial` = the partner's latest `clearing`/`pi`/`ti` accounts, `id` = the received payment the person chose from the projection; decision: `{payment_id, credited_as_of? (only within 2.1 rule 1's channel policy), designation_override? (2.4, with a reason)}`.
   - `payment_reverse.reverse`: `state` and `custodial` as above, the original payment's posted allocation from the record; decision: `{payment_id, reason ∈ {returned_item, misapplied, duplicate, fraud, correction}, return_code?, nsf_fee? boolean}` — money: `officer`.
   - `le_review.approve` / `cd_review.deliver` / `cd_review.receipt` / `cd_review.corrected`: the 21.2 / 25.2 service hydrated by 35.1 for the application, the fee assembly from the record, the delivery channel from the borrower's consents; decision: `{disclosure_id, method?, received_on? (only for a paper receipt the person holds), reason (corrected CD)}`.
   - `conditions.clear` / `conditions.reopen` / `conditions.ctc`: the condition row and its evidence documents from 23.3's record; decision: `{condition_id, evidence_document_id?, note}`; `ctc` takes no decision fields — 23.3's `runCtcChecklist` is run by the deriver and `issueClearToClose` refuses on its own when a check fails.
   - `closing_schedule.confirm` / `.assign_notary` / `.open_session`: 26.2's closing row, 25.2's earliest consummation (`computeEarliestConsummation` run by the deriver), the notary roster; decision: `{closing_id, slot_at (must be ≥ earliest consummation), notary_id?}` — the slot the borrower picked through 32.7 is the default.
   - `funding_release.release`: 35.6's orchestration at step `funding_authorized` (`waiting_human{funding_approver}`, 35.6 rule 4); the deriver runs 26.3 `evaluateFundingConditions` with facts from the record and refuses `GATE_CLOSED{codes}` before the release; decision: `{funding_id, wire_id}` — role `funding_approver`, dual control by 26.3's own four-eyes rule (the preparer and the approver are distinct staff users).
   - `escrow_analysis.run` / `.approve`: 3.1's `runEscrowAnalysis` over the escrow ledger, the disbursement schedule and the tax/insurance bills from the record; decision for `run`: `{analysis_year, effective_on}`; for `approve`: `{analysis_id}` (`officer` when the analysis changes the escrow payment by more than 3.1's tolerance — a money field).
   - `payoff_quote.quote` / `.statement`: 16.1's `computePayoffQuote` inputs — UPB, LPI, accrual method, rate segments, unpaid late charges, escrow balance, NIB balances, release fees from `jurisdiction_rules.payoff` — from the ledger and `loan_terms`; decision: `{requester_kind, good_through, delivery ∈ {portal, mail, fax}}`; a person can never enter a component figure — an override is 16.1's `officer` path, logged as a money-field proposal.
   - `lossmit_decision.decide`: 12.2's evaluation, the complete-application date and 12.4/12.5's plan terms from the record; decision: `{request_id, disposition ∈ {approve, deny, counter}, option_code?, denial_reasons? (12.2's codes)}` — a denial routes to `lossmit_reviewer` as 12.2 requires.
   - `foreclosure_case.refer` / `.instruct` / `.hold` / `.milestone`: 13.1's gate evaluation run by the deriver (never asserted by the person), the case row, the attorney firm; decision: `{case_id, firm_id?, instruction_code?, hold_reason?, milestone_code?, occurred_on?}`.
   - `bankruptcy_case.docket` / `.apply_trustee` / `.apply_postpetition` / `.statement_mode`: 14.1's case row, the ledger snapshot, the plan; decision: `{case_id, docket_entry_id?, amount_cents? (the trustee cheque — the person is its source), received_on?, mode?}` — the two `apply_*` actions are money fields (`officer`).
3. **The derived input is evidence.** Before dispatch the canonical JSON the tool will receive (derived fields plus decision fields, keys sorted, cents as strings) is hashed and stored through 35.2 as `work-derivation.json` with its `sources` (sequence numbers and versions read); `work_derivations.input_sha256` is what the tool's `agent_decisions.inputs_snapshot_hash` must equal (T4). A dry run (`work.screen.derive`) writes the derivation row and document and nothing else.
4. **Roles are the tool's, checked before the read.** `work.screen.read` lists an action as `available: false, needs: <role>` when the session lacks the role; `work.screen.act` answers `ROLE_REQUIRED{role}` before deriving; the role sent to the bus is the role the person named for the act (`x-staff-role` / body `role`) when the account holds it and the tool accepts it (src/console/server.ts:274 `chooseRole` in act mode, :446-450 the tool's gate); a held role the tool does not accept is refused 403 `ROLE_REQUIRED{role, held, act_as}` with the accepted held roles offered, never silently replaced by a greater one (34.1 rule 3 as amended 2026-09-15) — never a role the person does not hold, never admin (34.1: admin touches no borrower).
5. **Money-field actions are two people.** An action whose tool declares `moneyFields`, or that the screen registers as `money`, executes only for an `officer`; for any other role it is written as `proposed` (the derivation stored, `work.action.proposed{action_id, tool, input_sha256}` emitted, the item `waiting_approval`, `SM_WORK_APPROVAL_1BD` armed). A distinct `officer` decides: `approved` re-derives (rule 6), executes with the approver as actor and `approved_by = {proposer, approver}`, writes the executed `work_actions` row with `approval_of`; `declined` writes the approval row and returns the item to `claimed`. Proposer = approver is refused `SAME_PERSON`. This is 34.4's `NO_MONEY_FIELD` for the console applied to the one place the console now touches money: the officer runs the section's own tool; the screen adds no waiver of its own.
6. **Approval re-derives; a changed record refuses.** On `approved` the deriver runs again; if `input_sha256` differs from the proposal's, the act is refused `STALE_DERIVATION{proposal_sha256, current_sha256}`, the proposal is marked `declined` with that code and the item returns to `claimed` for a fresh proposal — a payment received or a ledger set posted between proposal and approval never executes against the old state.
7. **One act, one log row, one decision record.** Every `work.screen.act` (executed, proposed, refused or errored) writes exactly one `work_actions` row, one `staff_actions` row (34.1's, `command = <process> <tool>`, `role` = the role that acted — migration 0139) and, when a command ran, links the `agent_decisions` row the tool wrote and the first `loan_events` row of the command; a refusal writes the `work_actions` and `staff_actions` rows and nothing else (the unit of work rolled back). The action log is these three tables joined; rule 10 proves the join holds.
8. **The queue is the console's, widened.** `work.queue` returns the five console kinds unchanged (pg-store.ts:85-89's role filter kept) plus `job_dead`, `orchestration_held`, `approval_pending` and `case_milestone`, each mapped to a `screen_code` by the source: an escalation from 2.x → `payment_post` or `payment_reverse` by its `kind`; from 3.x → `escrow_analysis`; from 16.x → `payoff_quote`; from 12.x → `lossmit_decision`; 13.x → `foreclosure_case`; 14.x → `bankruptcy_case`; 23.3 → `conditions`; 25.2 / 21.2 → `cd_review` / `le_review`; 26.2 → `closing_schedule`; 26.3 / 35.6 → `funding_release`; anything else opens the 34.4 escalation view. An item is opened once per source (`source_kind, source_id` unique while open) by the sweep's queue pass and closed by the source's own closing event or by the person.
9. **Claims are short and visible.** A claim is one person for 4 hours (`SM_WORK_ITEM_CLAIM_4H`); a second person's claim answers `CLAIMED_BY_OTHER{staff_user_id}` (the id, never the name — 34.2's masking); a lapse returns the item to `open` and counts; the third lapse opens the `ops_analyst` escalation. A claim is not a lock on the loan — 35.1's lease is; two people acting on one loan serialize on the lease and the second sees `STALE_DERIVATION` if the first changed what the second derived from.
10. **The daily reconciliation.** `work.log.recon{as_of_date}` checks every `work_actions` row of the day: an `executed` row has its `staff_actions`, `agent_decisions` and `command_event_id`; a `refused` row has its `staff_actions` row and no event; every `derivation_id` resolves to a stored document whose sha-256 equals `input_sha256` (35.2's `documents.verify`); every current `work_screen_versions.actions[].roles` equals the tool's `humanRoles` and `money` equals `moneyFields ≠ []` in the registry now loaded (a mismatch is a stale screen: `stale_screens + 1`, the screen's actions are marked `available: false` until re-registered). The run also counts the day's `sole_officer_money_acts` — executed money-field actions with no `approval_of`, an `officer` acting alone under rule 5 — which 34.1 rule 6's access review lists for the quarter. The run writes `work_log_recon_runs` and emits `work.log.recon.run_completed{as_of_date, actions_checked, orphans, stale_screens, sole_officer_money_acts}`; orphans or stale screens > 0 open a sev 3 `compliance` escalation with the report document.
11. **Never a clock, never a notice, never a ledger line of its own.** The screens satisfy no timer (the owning tool's events do), send no notice (16.1's `sendNotice`, 3.1's `sendNotice`, 25.2's `deliverDisclosure` do, dispatched as actions) and post no ledger set; §35.8 owns no NTC code and no `rule_ref`.

#### AI agent design (AI-first)
`case` agent (tools: `work.queue`, `work.item.open`, `work.item.claim`, `work.item.release`, `work.item.close`, `work.item.cancel`, `work.screen.read`, `work.screen.derive`, `work.screen.act`, `work.action.propose`, `work.action.decide`, `work.log.recon`, `writeDecision`). End-to-end: unprompted, every sweep, the agent runs the queue pass (`work.item.open` for each new source event, mapped to a screen by rule 8), the claim-lapse handler and, once a day, `work.log.recon`; for an open item it may run `work.screen.derive` and attach the dry run's derivation to the item so the person opens a screen with the engine's view already computed; it proposes (`work.action.propose`) a disposition with a rationale where the owning section's agent has already decided (a 2.1 allocation plan, a 12.2 evaluation outcome, a 13.1 gate result). It never claims, closes, decides or executes: `work.screen.act`, `work.item.claim`, `work.item.close` and `work.action.decide` are `humanOnly` on the bus (`allow.agents = false`), and the FAKE reviewers (35.7) approve only through those same tools as `human:FAKE:<role>` — never in production. Decision record schema `{screen_code, screen_version, action_code, subject_kind, subject_id, decision_sha256, input_sha256, tool, role, by, approval_of?, rule_set_version: work.v1, model_version: deterministic, prompt_version: 35.8-v1, confidence: 1, rationale}`; the agent's proposals carry the owning agent's `model_version` and `confidence` alongside. Guardrails: `NO_CLIENT_STATE` (rule 2), `ROLE_REQUIRED` (rule 4), `TWO_PERSON_MONEY` and `SAME_PERSON` (rule 5), `STALE_DERIVATION` (rule 6), `HUMAN_ONLY_ACT` (no agent executes a screen action), `NO_CLOCK_EDIT`, `NO_NOTICE_OF_OWN`, `NO_LEDGER_OF_OWN` (rule 11), `NO_PII_IN_LOG` (34.1). Escalations: `ops_analyst` for an aged item and a thrice-lapsed claim; `officer` for a pending money-field proposal and a five-day-old item; `compliance` for a reconciliation with orphans or a stale screen; `underwriting_reviewer`, `funding_approver`, `mlo_of_record`, `lossmit_reviewer`, `attorney`, `settlement_agent` are the roles the screens route to, as the owning tools name them.

#### Edge cases and failure modes
- The owning tool refuses (a 2.1 guardrail, 23.3's checklist, 26.3's gate) → the unit of work rolls back; `work_actions.status = refused` with the tool's code; `staff_actions.result = refused`; the item stays `claimed`; the derivation row and document remain as evidence of what was attempted.
- The tool throws → `status = error`, the message class only (never the input) in `refusal_code`; a sev 3 `ops_analyst` escalation after the third error on one item.
- A subject the session may not read (34.2's role masking) → `work.screen.read` answers 404 `NOT_FOUND` before naming the subject; logged as `refused`.
- Two sessions act on one loan at once → 35.1's lease serializes them; the second's derivation is re-hashed inside the lease and refused `STALE_DERIVATION` if the first changed a source it read.
- The 18.1 kill switch is tripped for `case` → the queue pass and the daily reconciliation still run (they are deterministic, `model_version: deterministic`); only the agent's proposals stop, and the screens show no proposal.
- A screen version is stale (rule 10) → its actions are `available: false, needs: re-registration`; `work.screen.act` answers `SCREEN_STALE{code, version}`; reads continue.
- A proposal expires (one business day after `SM_WORK_APPROVAL_1BD` breaches, unattended) → `status = expired`, the item returns to `claimed`, the officer escalation stays open until completed through 34.4.
- An item whose source closes while claimed (the borrower pays through 32.x, the timer satisfies itself) → closed by the source event with `disposition = source_closed`; the claim is released; the person's next act answers `ITEM_CLOSED`.
- A demo-clock advance (35.3 rule 10) → the queue pass runs inline per crossed day; claims lapse on the demo clock, not wall time; the reconciliation runs once per crossed day.
- `FAKE_REVIEWERS=on` (35.7) → the fake approves a `proposed` money action as `human:FAKE:officer` through `work.action.decide` after the delay, with `SAME_PERSON` still enforced (the FAKE id differs from any staff user); under `ENVIRONMENT=production` the fake is refused and the item waits for a person.

Should a screen let a person enter a figure anywhere other than the fields listed as the person's source (a cheque amount, a trustee payment, an approved annual disbursement)? **Default: no; every other figure comes from the record, and an override is the owning section's `officer` path, logged as a proposal.**
2. Should the claim be a lock on the loan? **Default: no — 35.1's lease is the lock; the claim is coordination, and `STALE_DERIVATION` catches the race.**
3. Should the HTML `work` view ship in the same commit as the two tools? **Default: the tools and their T-ids first; the view is a thin client added once T1–T16 pass, tested by the deploy walk.**
4. Which roles may `cancel` an item? **Default: `ops_analyst` with a reason; a cancelled item whose source is still open is re-opened by the next queue pass, so cancel is only for a source that is gone.**
