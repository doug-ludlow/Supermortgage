### Blueprint row
The hosted runtime today is one transactional command bus over Postgres: a command hydrates the loan's events, ledger sets, open timers and every version of every entity row in scope, runs the section's synchronous domain code, and commits events, balanced ledger sets, timer upserts, decisions, entity versions and escalations atomically or not at all (src/runtime/app.ts:189-216; src/infra/db/unit-of-work.ts:77-124). Four things are missing between that bus and an operation that runs unattended on 1..N instances plus a separate sweep job. (1) The 426 entity kinds the tools write are versioned JSON in `entity_records` (db/migrations/0056_entity_records.sql, 0115_entity_records_scope.sql) and only 77 of the 770 tables the migrations create are INSERTed by non-test source, so no cycle, report, queue or constraint can read a relational row; hydration loads every version of every row in scope and every global row (src/infra/db/entities.ts:46-53), so latency grows with history. (2) Nothing serializes two commands on one loan or two sweeps on one book: hydration runs outside the transaction (unit-of-work.ts:82-88), the timer upsert is last-writer-wins (src/infra/db/timers.ts:34), the due query takes no lock (timers.ts:52-53), and Cloud Scheduler fires the sweep every minute with a 180 s attempt deadline (infra/terraform/scheduler.tf:8,11) against a 300 s job (run.tf:347) with no lease. (3) The outbox is counted, never dispatched: the sweep's only touch of `integration_messages` is a `GROUP BY status` (app.ts:306), `PgOutbox` has no non-test constructor call (src/infra/integrations/pg-outbox.ts:18), and 16.3 writes its Fannie Mae execution package into JSONB under the kind `integration_messages` (src/app/tools/section16-3.ts:259) where no dispatcher will find it. (4) Three service keys never exist on the runtime — `boarding` (section01.ts:36), `orig-boarding` (section30-2.ts:22) and `tolerance-21-5` (section25-1.ts:68, section25-2.ts:123) — so those tools answer 501 `not_wired` (src/app/tools.ts:85 → src/runtime/server.ts:385); and the stateful origination services (25.2's `ClosingDisclosureService` with eight private Maps, ops-25-2.ts:343-351; 21.2's `LoanEstimateService`, ops-21-2.ts:292-294; 21.3, ops-21-3.ts:374-375; 21.5, ops-21-5.ts:294; 29.1, ops-29-1.ts:412-413; 29.3, ops-29-3.ts:536-543; 29.4, ops-29-4.ts:427; 30.2, ops-30-2.ts:501) are constructed once per `Runtime` (src/runtime/origination.ts:362-380) and never rehydrated, so a CD prepared by one instance is "no CD" on the next, in the sweep job and after every deploy — the LE-deeming sweep already works around it by re-appending the service's own events by hand (origination.ts:443-460). This process is the seam that closes all four: typed rows projected in the command's transaction, bounded hydration with a declared history set, an expected-version guard, a per-loan lock and a sweep lease, the outbox dispatched by every sweep, the three keys wired, and every stateful service rebuilt from the record before each command.

### Verified requirement (as of 2026-09-15)
**Append-only, balanced, bigint (docs/ARCHITECTURE.md conventions 1, 3, 4).** `loan_events`, `ledger_lines`, `agent_decisions` and `boarding_validations` are never updated or deleted (Postgres triggers, `forbid_mutation()`); every ledger entry set balances or is rejected at COMMIT; money is `bigint` cents. A projector therefore copies figures the owning section already computed and rounded; it never computes a cent. **VERIFIED** against 0001_baseline.sql and 0003_cashiering.sql (`payment_allocations_immutable`, :68; `payments` has no mutation trigger and is upserted).

**The unit of work is the only write path (ARCHITECTURE conventions 5–7; app.ts:189-216).** Events are appended before the commit hook (unit-of-work.ts:113 vs :119) against plain foreign keys (`loan_events.loan_id → loans`, 0001_baseline.sql:263), so a projector that must create the row an event references (a boarding's `loans`, `parties`, `properties`, `custodial_accounts`, `transfer_batches`) runs in `opts.before` (:112) and a projector that records a fact runs in `opts.commit` (:119). **VERIFIED** at HEAD.

**2.1 fixes `payments` (spec/sections/02-…/2-1-…md:58).** "`payments` (baseline table, fixed here; all money `bigint` cents; retention `life_of_loan_plus_4y`; payer bank data encrypted)" — the column set is 0003_cashiering.sql:18-47 (`amount_cents bigint CHECK (> 0)`, `received_on`, `credited_as_of`, `idempotency_key UNIQUE`, `retention retention_class DEFAULT 'life_of_loan_plus_4y'`); allocations are `payment_allocations(payment_id, sequence, bucket, amount_cents, ledger_entry_set_id, rule_ref, credited_as_of)` with `UNIQUE (payment_id, sequence)` (:55-67). The typed row is the spec's row, not a new one. **VERIFIED.**

**History readers (src/app/tools/section02.ts:114,272; section04.ts:57; section06.ts:238; section17-3.ts:95).** Four `payments.history` tools and 17.3's first-version gate (`rt.store.history("counterparty_notifications", r.id)[0]?.data.status === "planned"`) depend on the store holding every version of those kinds. Latest-version hydration must load a declared `HISTORY_KINDS` set in full. **VERIFIED.**

**Advisory locks and `SKIP LOCKED` (PostgreSQL 16 manual, §13.3.5 "Advisory Locks"; SELECT "The Locking Clause").** A transaction-level advisory lock (`pg_advisory_xact_lock`) is released at commit or rollback; a session-level lock (`pg_advisory_lock` / `pg_try_advisory_lock`) is held until unlocked or the session ends — a lease held this way cannot go stale, it dies with its connection. `FOR UPDATE SKIP LOCKED` lets concurrent claimers each take distinct rows. Two precedents already in the tree: `pg_advisory_xact_lock(hashtext('du_row_identity'), hashtext($1))` (src/domain/underwriting/du/writer.ts:170) and the card lock (src/runtime/borrower/commands.ts:221); the session-level pattern on a dedicated `pg.Client` is src/infra/db/test-lock.ts:15-20. **[PARTIALLY VERIFIED — the manual is cited from memory; the two in-tree precedents are verified at HEAD.]**

**The scheduler overlaps (infra/terraform/scheduler.tf:8,11,14; run.tf:346-348).** `schedule = "* * * * *"`, `attempt_deadline = "180s"`, `retry_count = 1`; the job's `timeout = "300s"`, `max_retries = 1`. A job execution that runs longer than a minute is still running when the next firing starts a second execution. **[UNVERIFIED — whether Cloud Run jobs refuse a second concurrent execution of the same job by default; the build assumes they do not and leases in the database.]**

**Retry policy of the outbox (src/infra/integrations/outbox.ts:77,129-155).** `DEFAULT_RETRY = { maxAttempts: 5, baseDelayMs: 60_000, maxDelayMs: 30 * 60_000 }`, exponential backoff, `dead` after the fifth attempt or at once on an `unavailable` failure with a `human_portal_tasks` row for the adapter's owner role (:149-153). The dispatcher exists and is tested; it is not constructed by any runtime path. **VERIFIED.**

**Discrepancies vs blueprint**: (1) The gap assessment names three unwired keys where the §35 plan (written at d1238cc) said "the 501 gap is 1.1 only"; HEAD agrees with the assessment — `tolerance-21-5` is looked up by 25.1 and 25.2 while origination.ts:373 registers the same class under `tolerance`, and `orig-boarding` is looked up by every 30.2 tool — so the build wires all three (rule 10). (2) The plan put the server-side cash state (its 35.1-T10) and the generic notice save (its T6) here; at HEAD those belong to 35.5 (the installment schedule and the daily cashiering cycle) and 35.2 (documents and artifacts); this file keeps the seam, the guards, the locks, the outbox, the keys and the rehydration. (3) The plan numbered the seam's migration 0133; migrations now run to 0140 (db.test.ts:40 counts 776 base tables through 0136) and 0141–0149 are reserved for the main branch's concurrent work, so 35.1's are 0150 and after, append-only (0150 creates the eight seam tables and the view; db.test.ts counts 784). (4) The plan hydrated the stateful services "keyed boarding|transfer|fpi" and left the origination Maps as they are; the assessment's "process-local state" gap (blocking) is closed here for every stateful service, origination and servicing, by the same contract (rule 9).

### Build spec
#### Inputs and triggers
- Every bus command: `Runtime.executeDef` (app.ts:189) → `PgUnitOfWork.run` — the seam is the unit of work, not a tool a caller invokes.
- `POST /v1/sweep` and the `sweep` job (src/runtime/main.ts:58-70) → the lease, the outbox drain, then the passes the sweep runs today.
- `record.project{kind, entity_id?}` — a person or the daily run projects one kind's un-projected versions; `record.replay{kind, scope_key?, dry_run}`; `record.gaps{as_of_date}`; `record.verify{as_of_date, kinds?}`; `record.snapshot{service_key, application_id | loan_id}`; `record.lease{op: status | list}`; `outbox.dispatch{adapter?, limit?}` (the sweep's own call, also runnable by hand).
- Events the seam reacts to: every persisted event of a command (projectors read the command's `store.versionsSince(mark)`, not the event types); `integration.message.queued{message_id, adapter}` (this process's, emitted by the outbox enqueue on the command path); `outbox.requeued{message_id}` (34.4's).
- Events that arm this process's clocks: `projection.run_completed{run_id, as_of_date, kinds_checked, rows_verified, mismatches, gaps}`, `sweep.run_completed{run_id, as_of_date, holder, duration_ms, passes}`, `integration.message.dead{message_id, adapter, attempts, error, dead_at}`.
- Input revival: a tool's JSON `input` has every `*_cents` field revived to bigint (ARCHITECTURE "One runtime"); a projector never sees a `number` for money — a `number` in a money column is a `schema_mismatch` gap, never a cast.

#### State machine
Per entity version (`entity_projections` presence): `written —(projector in before/commit; same transaction)→ projected`; `written —(no projector)→ gap{no_projector}` (the version stands in JSONB; the daily run lists it); `written —(projector threw)→ command rolled back` (nothing is written: not the version, not the row, not the event). Terminal: `projected`. A replay moves `gap → projected` by `record.replay`, never by hand.
Per command (the unit of work): `received —(lock taken: pg_advisory_xact_lock on the scope)→ hydrating —(expected versions match)→ running —(fn returned)→ committing —(COMMIT)→ committed`; `hydrating —(expected version differs)→ refused{STALE_RECORD}`; `committing —(entity_records PK collision from a concurrent writer)→ refused{STALE_RECORD}`; `running —(threw)→ rolled_back`. Terminal: `committed`, `refused`, `rolled_back`. No human transition.
Per sweep run (`sweep_runs.outcome`): `running —(every pass returned)→ completed`; `running —(a pass threw and was not caught: the lease or the drain)→ failed`; a firing that finds the lease held writes `skipped{lease_held}` and exits 0. The session lock is released by `pg_advisory_unlock` at the end or by the session's death; a `running` row whose `heartbeat_at` is older than 10 minutes is shown as `stale` by `record.lease{op: status}` and is evidence, not a lock — the next firing takes the lock because the dead session no longer holds it.
Per outbox message (`integration_messages.status`, outbox.ts:13): `queued —(claimed by a drain: FOR UPDATE SKIP LOCKED)→ sent | acked` (the adapter's ack) `| queued{attempts+1, next_attempt_at = backoff}` (retry) `| dead` (fifth failure, or `unavailable` at once, with the `human_portal_tasks` row the dispatcher already opens); `dead | failed —(34.4 requeue)→ queued`. Terminal: `acked`, `rejected`, `duplicate`.
Per stateful service instance: `constructed —(hydrate: snapshot at through_sequence + events after)→ current —(command)→ dirty —(commit)→ discarded` (one instance per command; nothing survives the command but the record). Who: the runtime, always; no role.

#### Business rules and calculations
1. **A kind is typed when the spec fixes it, a cycle reads it across loans, a typed table must reference it, or a service must survive a restart.** 2.1's "`payments` (baseline table, fixed here …)" is the rule's model: the section's Data model names the table and its money, date, retention and encryption columns; the projector maps the kind's JSON fields onto those columns by an authored map in `src/domain/operations-runtime/projectors/<section>.ts` (one exported map per kind: `{ kind, table, mode: insert | upsert, phase: before | commit, columns: { json_field → column }, history: boolean }`). Everything else stays JSONB and is a listed gap, never an invisible one.
2. **Two projector phases, one transaction.** A row projector (a kind an event, timer or escalation references by foreign key: `loans`, `parties`, `properties`, `custodial_accounts`, `transfer_batches`, `applications`) runs in `opts.before` (unit-of-work.ts:112), before `events.append` (:113), from `store.versionsSince(mark)`; a fact projector runs in `opts.commit` (:119) after events, ledger sets, timers and decisions. Both are inside `db.tx`: a projector that throws rolls the command back whole — no entity version, no event, no ledger line, no typed row (T4). Each projection writes one `entity_projections` row.
3. **A projector copies; it never computes.** The columns it writes are the JSON fields the owning section computed and rounded (convention 1: "rounded once, half-up, at the point the spec says"); a money column takes a bigint or the projection is a `schema_mismatch` gap; a projector holds no arithmetic beyond `sum` for a verify check. Where the section's ledger set exists, the verify run checks the typed sum against the set's lines by `rule_ref` (worked example A). Guardrail `PROJECTOR_NEVER_COMPUTES`.
4. **Upsert where the baseline table is mutable, insert where it is append-only.** `payments` has no mutation trigger (0003_cashiering.sql) and 2.1's later versions (identified, allocated, reversed) update the same row; `payment_allocations` has `payment_allocations_immutable` (:68) and each version's allocation lines are inserted once under `(payment_id, sequence)` — a re-projection of an already-inserted version is a no-op by the `entity_projections` unique key, not a duplicate-key error. `loans.status` is already updated by `projectStatus` (unit-of-work.ts:114); the seam adds no second writer of that column.
5. **One uuid per legacy ref.** A store id like `fees-3` or `sel-2` (tools.ts:164) is not a uuid and repeats across scopes (0115); the projector mints a uuid once per `(kind, legacy_ref, scope_key)` in `entity_keys` and every later version and every replay reuse it; a typed row's `id` is that uuid; the JSON version keeps its legacy id untouched (T12).
6. **Hydration is bounded.** The entity load for a command is at most three queries whatever the history: the scope's latest versions from `entity_latest_scoped`, the full history of `HISTORY_KINDS` (`payments`, `counterparty_notifications`, and any kind whose authored map says `history: true`) for the scope, and the latest global rows (`scope_key = ''`); `payments.history` (section02.ts:114,272; section04.ts:57; section06.ts:238) and 17.3's first-version read (section17-3.ts:95) answer exactly what they answer today (T3). The events, ledger sets and open timers load as before (unit-of-work.ts:82-88) but inside the transaction (rule 7).
7. **One loan, one writer.** `PgUnitOfWork.run` opens the transaction first, takes `pg_advisory_xact_lock(hashtext('uow'), hashtext(<loan_id>))` and, for an application scope, `pg_advisory_xact_lock(hashtext('uow'), hashtext(<application_id>))` (both, in that order, for the 30.2 hand-off scope), then hydrates, runs, persists and commits; a global command (no loan, no application) takes `hashtext('uow:global')`. Two commands on one loan serialize; two loans never wait for each other (T6). The lock is transaction-scoped: it dies with the transaction, so nothing is ever left locked.
8. **The expected-version guard.** A command may carry `expected_versions: [{kind, id, version}]`; after the lock, the runtime compares each with `entity_latest_scoped` and refuses `STALE_RECORD{kind, id, expected, current}` (HTTP 409) before the domain code runs — no event, no version, no decision (T2). Without a declared expectation the guard is still mechanical: `entity_records`' primary key `(kind, id, version, scope_key)` (0115) makes a concurrent writer's `version + 1` collide at INSERT; the unique violation is mapped to the same `STALE_RECORD` and the transaction rolls back. Rule 7 makes the collision impossible within one loan; the guard covers global rows (rate sheets, calendars, the LLPA matrix) that many loans read-then-bump. Guardrail `STALE_RECORD_REFUSES_WHOLE_COMMAND`.
9. **A stateful service is rebuilt from the record before every command.** `originationServices.forCommand` (origination.ts:362-380) constructs a fresh instance of each stateful service per command instead of one per runtime; each service exposes `hydrate(snapshot: State | null, events: readonly DomainEvent[])` that folds its own event types (the ones its `append` writes: `disclosure.cd.*`, `disclosure.le.*`, `fee.baseline.set`, `tolerance.*`, `lock.*`, `commitment.*`, `delivery.*`, `enote.*`, `boarding.*`) into its Maps; the unit of work's hydrated history is the input, so no extra query is needed for the tail. The servicing keys `boarding`, `transfer` and `fpi` (BoardingService's seven maps and counters, src/domain/boarding/service.ts:85-91; TransferBatchService's batches, portal tasks and escalation subscription, transfers/inbound.ts:168-172; Fpi92Service's cases, placements and requests, insurance/ops-9-2.ts:93-96) are hydrating adapters of the same contract, rebuilt from the typed rows their projectors wrote plus the loan's events. `service_snapshots` is an accelerator only: `record.snapshot` folds the state through `through_sequence` and stores it with `state_sha256`; a hydration from snapshot + tail must equal a full replay (T14) or the snapshot is discarded and a `ciso` sev 2 escalation opens. The LE-deeming sweep (origination.ts:443-460) becomes a call to `LoanEstimateService.deemReceived` on a hydrated instance; its hand-written re-append is deleted. Guardrail `REPLAY_IS_IDEMPOTENT`.
10. **The three keys are wired, on the bus, with parity.** `tolerance-21-5` is the `tolerance` instance registered under a second key (the same object; a tolerance test run by 25.1 or 25.2 is 21.5's run, T9). `orig-boarding` is `OriginationBoardingService` hydrated from the application's events and `applications`/`loans` rows. `boarding` is the `BoardingService` adapter; `1.1 boardLoan` on the bus writes, in `opts.before`, exactly the set `POST /v1/transfers/batches` writes today — `transfer_batches`, `properties`, `loans`, `borrowers`, `loan_borrowers`, `loan_terms`, `transfer_batch_loans`, `boarding_validations` (src/runtime/transfers.ts:127-162), `parties` (:175-177), `custodial_accounts` (:181-183) — then its events, the 1.6 opening ledger sets (:160), timers (:161), escalations (:162), the global `transfer_batches` entity row (:170) and one `agent_decisions` row (T10). `src/runtime/transfers.ts` stays the seed path and refuses under `ENVIRONMENT=production` (config.ts:56 precedent).
11. **The outbox is drained by every sweep.** After the lease and before the passes, `outbox.dispatch` claims due rows per adapter with `SELECT … FOR UPDATE SKIP LOCKED LIMIT 100` (PgOutbox.due, pg-outbox.ts:32-34, gains the locking clause), runs the existing `OutboxDispatcher` (outbox.ts:129) with `DEFAULT_RETRY` (5 attempts, 60 s base, 30 min cap — unchanged; jobs in 35.3 use their own cap), writes one `outbox_dispatches` row per attempt and emits `integration.message.sent{message_id, adapter, attempt}` or `integration.message.dead{message_id, adapter, attempts, error, dead_at}`. A tool that writes the kind `integration_messages` to the store (section16-3.ts:259) is projected into the real outbox by `PgOutbox.enqueue` in `opts.commit` with the store id as idempotency key, so a second projection is `duplicate: true`, never a second message. 34.4's requeue (`outbox.requeued`) is picked up by the next drain like any queued row.
12. **The sweep is one execution at a time.** A sweep takes `pg_try_advisory_lock(35_001)` on a dedicated client (test-lock.ts:15-20 pattern); a firing that does not get it writes `sweep_runs{outcome: skipped, skipped_reason: lease_held}` and `sweep.run_skipped{holder}` and exits 0; the holder writes `sweep_runs{running}`, heartbeats every pass, and finishes with `completed` and `sweep.run_completed` in its own final transaction (so `SM_SWEEP_HEARTBEAT_DAILY` is satisfied and re-armed by the run that completes). The breach pass claims its due timers `FOR UPDATE SKIP LOCKED` (timers.ts:52-53 gains the clause) so a breach is evaluated once even if a lease ever failed. Guardrail `LEASE_DIES_WITH_SESSION` (no table row is ever the lock).
13. **The daily verify run.** At 06:00 ET (the recurring clock's hour) the sweep runs `record.verify{as_of_date}`: for every typed kind, every version since the last run has an `entity_projections` row (else a `projection_gaps` row), and for a sample of 100 rows per kind plus every money-bearing row written that day the typed columns equal the JSON version's fields and, where a ledger set exists, the typed sum equals the set's lines by `rule_ref`; one `projection_runs` row and `projection.run_completed`. A mismatch on a money column is `projection.mismatch_found` with a sev 1 `ciso` escalation and no correction by the run (T13); a mismatch on a non-money column is sev 3 `qc_officer`. `record.gaps` is the same report without the verify.
14. **No money field changes here.** A projector, a replay and a verify never write a money column except by copying the owning section's version; a correction is the owning section's command with its `officer` waiver (convention 6; T15). Guardrail `NO_MONEY_FIELD_CHANGE`.

**Worked example A (a 2.1 payment projected, verified to the cent).** Loan with UPB **$248,310.55**, note rate 6.500%, fixed P&I **$1,612.34**, escrow payment **$432.78**; 2.1 posts a conforming payment of **$2,045.12** (`amount_cents = 204512n`). 2.1 computes the interest as UPB × rate ÷ 12: 248,310.55 × 0.065 = 16,140.18575; ÷ 12 = 1,345.015479 → half-up to the cent → **$1,345.02** (`134502n`); principal = P&I − interest = 1,612.34 − 1,345.02 = **$267.32** (`26732n`); escrow = **$432.78** (`43278n`); check: 134,502 + 26,732 + 43,278 = 204,512 cents = the payment. The projector writes one `payments` row (`amount_cents 204512`, `received_on`, `credited_as_of`, `retention 'life_of_loan_plus_4y'`, `idempotency_key` = the version's own) and three `payment_allocations` rows in 2.1's order, `sequence 1..3`, `bucket` interest / principal / escrow, `amount_cents` 134502 / 26732 / 43278, each with the `rule_ref` 2.1 stamped and the `ledger_entry_set_id` of the balanced set 2.1 posted; the verify run sums the three rows to 204,512 and matches the set's lines by `rule_ref`. UPB after the post, as 2.1 wrote it on the version and the projector copied it: 248,310.55 − 267.32 = **$248,043.23** (`24804323n`). Nothing here was computed by the projector; every figure is 2.1's, copied, and the test asserts each to the cent.

- **`postgres`** (in-process; `pg_advisory_xact_lock` per scope, `pg_try_advisory_lock(35_001)` for the sweep on a dedicated client, `FOR UPDATE SKIP LOCKED` on the outbox and the due timers; idempotency by the primary keys of `entity_records`, `entity_projections`, `entity_keys` and `outbox_dispatches`; on outage every command fails closed with nothing written).

No new vendor.

#### AI agent design (AI-first)
`security-records` agent (tools: `record.project`, `record.replay`, `record.gaps`, `record.verify`, `record.snapshot`, `record.lease`, `outbox.dispatch`, `writeDecision`). End-to-end: the seam itself is not an agent act — projectors, locks and the guard run inside every command's unit of work with the command's actor; the agent's tools are the daily verify run (unprompted, from the sweep at 06:00 ET), the gap report, a replay of one kind into its typed table after a projector is authored or fixed (idempotent; dry-run first, then the write, both logged with counts), a service snapshot after a long application history, the lease status and the outbox drain the sweep calls. What it proposes for a human: nothing about money — a money mismatch is a sev 1 `ciso` escalation with the row ids and the owning section named; the correction is that section's officer command. What it never does: compute or write a money column, break a lease, delete or update an `entity_records`, `entity_projections` or `outbox_dispatches` row, or replay into a table under a legal hold. Decision record schema: `{run_id | kind | message_id, action ∈ {verify, replay, snapshot, dispatch}, scope_key?, versions, rows_written, mismatches, gaps, state_sha256?, rule_set_version: records.v1, model_version: deterministic, prompt_version: 35.1-v1, confidence: 1, rationale}`. Guardrails: `PROJECTOR_NEVER_COMPUTES`, `NO_MONEY_FIELD_CHANGE`, `STALE_RECORD_REFUSES_WHOLE_COMMAND`, `REPLAY_IS_IDEMPOTENT`, `LEASE_DIES_WITH_SESSION`, `OUTBOX_RETRY_CAP_5`, `NO_PII_IN_DECISION` (ids and column names only), `HOLD_BLOCKS_REPLAY`. Escalations: `ops_analyst` for a day without a verify run or a sweep, a dead letter unreviewed, or a kind whose gap count grows two days running; `ciso` for a money-column mismatch (sev 1) or a snapshot that differs from replay (sev 2); `qc_officer` for a non-money mismatch; `officer` for the correction of any typed row that carries money, through the owning section's command.

#### Edge cases and failure modes
- A projector is authored for a kind with existing JSONB history → `record.replay{kind}` walks every scope's versions oldest first, mints keys once, inserts append-only targets once per version and upserts mutable ones to the latest; a second replay writes zero rows and zero events (T12).
- A command's `before` projector needs a row another projector in the same command creates (a boarding's `loans` after `properties`) → the authored map declares `after: [kind]`; the seam orders projectors topologically per command and refuses a cycle at startup, not at runtime.
- The same legacy ref is written by two scopes (`sel-2` on two applications, 0115) → two `entity_keys` rows, two uuids; never a cross-scope collision.
- A concurrent global-row writer (two sweeps' rate sheets, two journeys' LLPA matrix) → the second commit collides on the `entity_records` primary key and is refused `STALE_RECORD`; the caller re-reads and re-runs; nothing partial is written.
- The sweep's dedicated lock client cannot connect → the run is `failed{lease_unavailable}` before any pass; exit 1; the next minute tries again; `SM_SWEEP_HEARTBEAT_DAILY` breaches after a day of failures, not a minute.
- The job is killed at 300 s mid-pass → its session dies, the lock is released by Postgres, the `sweep_runs` row stays `running` with a stale heartbeat (shown as `stale`), the next firing takes the lock and runs; every pass is a transaction, so nothing half-committed exists to repair.
- `SM_SWEEP_HEARTBEAT_DAILY` can only breach inside a sweep → an outage is escalated by the first sweep that runs after it, with the breach dated to the missed day; the escalation is the record that the day had no sweep.
- A dead message whose adapter is FAKE is requeued by 34.4 → sent on the next drain, `integration.message.sent` satisfies `SM_OUTBOX_DEAD_LETTER_REVIEW_1BD`.
- A service's snapshot was taken at sequence N and the events after N include one the service does not recognize → the fold ignores it (the service never appended it) and the state hash still equals replay's; an unrecognized event never fails hydration.
- The typed target is under a legal hold (35.2's `document_holds` or a `loans.legal_hold`) → replay skips the scope with `projection_gaps{reason: key_conflict, detail: {hold: true}}` and the gap report says so; never a write under hold.
- A tool sends `expected_versions` for a kind the scope does not hold → `STALE_RECORD{current: null}`; the command never runs.

#### Audit and evidence
What an examiner is shown: for any typed row, its `entity_projections` chain back to the `entity_records` version and the command's first event (who, when, which tool), and for any JSON version the row it became or the `projection_gaps` row that says it has not; the daily `projection_runs` with their reports, mismatches and the escalations they opened; `sweep_runs` for every minute of the year with their passes, skips and stale rows; `outbox_dispatches` for every attempt at every message with the adapter's response hash; `service_snapshots` with hashes and the `sequence` they fold through; the `STALE_RECORD` refusals as the portal's `staff_actions` (34.1) and API logs record them (they write no domain row by design). ### Open questions / decisions
1. Should hydration of events, ledger sets and open timers move inside the transaction with the lock (rule 7), or only the entity load? **Default: everything inside — a command that read the loan before another's commit is exactly the race the lock exists to end; the cost is a longer transaction, measured in T6.**
2. Snapshot cadence for stateful services? **Default: no automatic snapshots; `record.snapshot` on demand and from the verify run for any application whose event count exceeds 500; T14 proves equality either way.**
3. Should the sweep lease be a table row with expiry instead of a session lock? **Default: the session lock is the lock and `sweep_runs` is the evidence; a row-with-expiry can go stale under a killed job, a session lock cannot.**
4. Which kinds are typed in the first wave? **Default: the money spine (`payments`, `payment_allocations`, `suspense_items`, `fees`, `autodraft_enrollments`), the boarding set (rule 10), the origination stateful kinds (`disclosures`, `locks`, `commitments`, `tolerance_tests`, `tolerance_cures`, `deliveries`, `purchase_advices`) and `integration_messages`; 35.3–35.6 add the kinds their cycles read as they land, each with an authored map and a replay.**
5. Does a `STALE_RECORD` refusal deserve its own event? **Default: no — it writes no domain row; the API log and 34.1's `staff_actions` carry it; 35.11 counts refusals from the log.**
6. Should 19.1 add a platform-evidence retention class shorter than `permanent` for the seam's rows (`sweep_runs`, `outbox_dispatches`, `projection_*`)? **Default: `permanent` (the enum's only class that outlives every loan-scoped one, 0001_baseline.sql:15) until 19.1 adds one by an append-only migration; counsel decides the term.**
7. Build decision (rule 7, the global lock): a global command that declares `expected_versions` takes `uow:global` before it reads; one that declares none takes it just before it persists, and only when it wrote a global row. A staff or portal command that touches no global row therefore takes no platform-wide lock (34.1-T5's two admins must interleave; 35.7/35.8 run every staff act as a global command), and the loser of an undeclared read-then-bump race is refused `STALE_RECORD` by the primary key (rule 8's mechanical guard). **Owner's call whether the spec's wording ("a global command takes hashtext('uow:global')") should be tightened to this or the build changed to serialize every global command.**
8. Build decision (rule 7, the command's connection): with hydration inside the transaction, a tool that read a table through the pool from inside a command needed a second pool connection, and four concurrent global commands deadlocked the pool of four (src/infra/db/client.ts:35). The runtime now hands every command a view of itself (`Runtime.commandView`) whose `db`, `uow`, `entities`, `escalationRepo` and `applications` run on the command's own connection (`transactionDb`: a nested `tx` is a savepoint), so a unit of work a tool runs inside a command commits with the command or not at all; the two 34.4 writes that must outlive a refusal (the fourth-requeue escalation, an expired kill-switch request) go through `rt.root.db`. **Default: keep; a refusal writes nothing of its own (open question 5) and the pool stays at 4.**
