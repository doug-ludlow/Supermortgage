### Blueprint row
Today the partner's tape reaches the platform through Supermortgage's own staff: someone at the partner sends the spreadsheet, an `ops_analyst` uploads it on `/ops` (34.3) or a machine token posts it to `/v1/partner-book/imports` (33.1), and the partner learns what happened by asking. This process puts the drop in the partner's own hands without touching what happens after it: a `partner_admin` drops the tape and the supplement on the Book page, the same `book.import` runs with the partner user as the actor and the partner taken from the session, and the partner reads the import report, the history of its uploads with what each changed, the status line ("book as of, next expected, late") and the loans the latest tape dropped. The partner sees the holds and cannot resolve them; the partner sees the invitations as counts and never writes to a homeowner; nothing on this page moves a dollar, arms a servicing clock or transfers servicing. The partner's incumbent subservicer keeps servicing every loan on the tape.

### Verified requirement (as of 2026-09-16)
**The import is 33.1's, dispatched with a partner actor (33.1 rules 1, 2 and 8; 34.3 rule 1).** The tape and the supplement are parsed under the named profile, the header row gates the whole file (`rejected` when a required column is absent, nothing of the book written), the same two files land once (`already_loaded` with the earlier import id on the `(partner_party_id, tape_sha256, supplement_sha256)` key), a later as-of date appends facts rows and rolls `loan_terms`, and a loan absent from a later full tape is held (`not_on_latest_tape`), never closed, until the next tape carries it or an `ops_analyst` resolves it. 34.3 already dispatches that import with a staff member as the actor; this process dispatches it with a partner user as the actor and adds no second import path. **[VERIFIED against src/runtime/partner-book.ts importPartnerBook — the profile gate before any write, the `already_loaded` answer, the `rejected` answer with `missing_headers`, the hold read by holdsOf from the import and facts rows — and 33.1-T3, T11, T12.]**

**The partner is the session's, never the body's (36.1; 16 CFR §314.4(c)(1); GLBA §1016.13).** A partner user is bound to one `parties{servicer}` row and every query of this process is filtered on it; a multipart field that names a partner, an NMLSR id or a profile is dropped before the parse; an import, a loan or a hold of another partner is `404 NOT_FOUND`, never `403`, because existence is not a signal. The partner's data is used for the partner's own program and shown to the partner's own users — the service-provider use §1016.13 permits without an opt-out — and to no one else through this door. **[VERIFIED — the rule text; the tenant rule is 36.1's and the brief's rule 5.]**

**Monitored, not serviced (33.1; 20.1 rule 1's universe).** A loan on the tape carries `loans.status = monitored`; the upload refreshes the partner's facts and arms only 33.1's clocks; no cashiering, escrow, delinquency, statement or ACH clock of sections 2–19 arms on `partner_book.*` events and every such command refuses `LOAN_MONITORED`. A tape drop is a GLBA service-provider data feed, not a post-delivery servicing transfer: no Form 629, no Form 101, no RESPA goodbye or hello letter, no custodial account for a monitored loan. **[VERIFIED against 33.1's verified requirement and 33.1-T9; the Fannie transfer forms are stated as out of scope by the brief §3 rule 9 and §12.]**

**No consumer report on import (FCRA §604(a); 33.1).** The tape's FICO lands as a fact of the partner's file (`representative_score`, `score_source = partner_file`, a pricing input after the homeowner's own Yes) and no report is ordered by an upload; the partner portal shows no score anywhere (36.3). **[VERIFIED — 33.1's verified requirement, unchanged.]**

**Discrepancies vs blueprint**: (1) 33.1's staff multipart carries `partner` and `profile` fields (33.1 Inputs); the partner's multipart carries neither — a field of either name is dropped, not honoured (36.2-T4), and the profile is the one 33.1 registers for the partner (`m3-v1`). (2) "No rows are written" for a wrong layout (36.2-T5) means no row of the book — no loan, facts, terms, party, invitation or clock; the record 33.1 keeps of a rejected attempt (its `rejected` import row and the `ops_analyst` work item) is 33.1's and stands. (3) The status line's "late" is the state of 33.1's clock, read; this process arms no clock and computes no date.

### Operational prerequisites
- 36.1: a `partner_admin` of the partner with an open session (the doors, the roles, the action log, the partner-grade mask); `partner_ops` and `partner_auditor` sessions for the read-only views.
- 33.1's registration of the partner (the `parties{servicer}` row with legal name and NMLSR id, the `partners/<id>` entity, the `partner_programs` row) and the profile `m3-v1`; in non-production the demo partner (`Northlight Mortgage Servicing (FAKE partner)`, NMLSR `1234567`) seeded by 33.1's seedPartnerBookDemo, so the first drop of the fixture answers `already_loaded`.
- The FAKE e-mail port in every build stage: 33.1's invitation leaves the import exactly as it does from `/ops`; this process sends nothing of its own. `INTEGRATIONS=fake` throughout.

### Build spec
#### Inputs and triggers
- `POST /v1/partner/book/imports` (multipart: `tape` as `.xlsx` or `.csv`, `supplement` as `.xlsx` or `.csv` when present, `as_of_date` as `YYYY-MM-DD`; actor = the session's `partner_admin`) → 33.1's `book.import` through importPartnerBook with `{partner: the session partner's servicer row, as_of_date, profile: "m3-v1", tape, supplement}` → the answer is the report partnerBookReport returns (`status ∈ loaded | rejected | already_loaded`, rows total and loaded, exceptions, created / updated / unchanged, parties created / linked, invitations sent and held, loans now on hold). A `partner_ops` or `partner_auditor` session → `403 ROLE_REQUIRED{role: partner_admin, act_as: []}` before either file is read.
- `GET /v1/partner/book/imports` → listPartnerBookImports for the session partner (the rows 34.3's `book.history` lists); `GET /v1/partner/book/imports/:id` → partnerBookReport (the report 33.1's `book.report` reads), `404 NOT_FOUND` when the import's `partner_party_id` is not the session's.
- `GET /v1/partner/book/status` → partnerBookStatus narrowed to the session partner: `as_of_date`, `next_expected` (the as-of date plus 7 calendar days, the due date of 33.1's `SM_PARTNER_BOOK_TAPE_EXPECTED_7`), `late`, `on_hold`, `monitored_loans`, `imports`.
- `GET /v1/partner/book/holds` → holdsOf for the session partner, projected through 34.3's hold queue with the partner-grade mask and without the resolve control. No `POST` under `/v1/partner/book/holds`; `POST /v1/partner/book/loans/:id/resolve` → `403 ROLE_REQUIRED{role: ops_analyst, act_as: []}` before any read.
- `GET /v1/partner/book/loans/:id` (the path 36.1-T3 exercises) → 34.3's `book.loan` for the session partner as a PartnerLoanRow (36.3's bucket, 36.5's detail), `404 NOT_FOUND` for a loan whose `partner_party_id` is not the session's.
- Events: none of its own. 33.1's `partner_book.import.completed`, `partner_book.loan.loaded`, `partner_book.loan.not_on_tape`, `partner_book.account.provisioned` and `partner_book.invitation.sent` are emitted by the import with the partner actor; 36.1's `partner_actions` row per request carries `book.import` as the action of the POST and `partner_portal.viewed` on a GET.

#### Data model
New tables: none — every row this process shows is 33.1's (the import row with its report, the facts, the invitations as counts and hashes, the hold read from the import and facts rows) and every row it writes is written by 33.1's `book.import` under the partner actor or by 36.1's action log; no column of 36's own is added to any of them.
- Baseline tables read: `partner_book_imports` (the history, the report, the status line), `partner_book_facts` (the latest as-of per loan; the hold is the facts row older than the partner's latest loaded import — 33.1 rule 8), `partner_book_invitations` (counts and hashes only), `loans` (`status`, `servicer_loan_number`, `partner_party_id`), `loan_terms`, `properties`, `parties` (the session partner's `servicer` row: legal name and NMLSR id for the import's partner and the page's banner), `borrowers`, `loan_borrowers`, `timers` (33.1's next-tape clock for the status line), `partner_sessions` and `partner_users` (36.1: the actor and its name).
- Baseline tables written: by 33.1's `book.import` with the partner actor — `partner_book_imports`, `partner_book_facts`, `partner_book_invitations`, `loans`, `loan_terms`, `properties`, `parties`, `borrowers`, `loan_borrowers`, `loan_events` (33.1's events), `agent_decisions` (33.1's decisions naming the partner actor), `notices` and `notice_deliveries` (33.1's invitation), `timers` (33.1's two clocks); by 36.1 — `partner_actions` (one row per request: `book.import` as the action of the POST with the import id as `subject_id`, `partner_portal.viewed` on a GET; no PII). Nothing else.

#### State machine
None of its own. Per import: 33.1's `received → loaded | rejected`, and `already_loaded` as the answer to a repeat of the same files. Per loan: 33.1's `monitored`, on hold (`not_on_latest_tape`) while absent from the partner's latest tape, `paid_off | transferred_out` only by the partner's tape marking it so or by an `ops_analyst`'s `book.resolve` on `/ops` — never by a partner user. Per request: 36.1's `requested → ok | refused`, one action-log row each.

#### Business rules and calculations
1. **The upload is 33.1's `book.import`, with the partner user as actor.** `POST /v1/partner/book/imports` runs 33.1's import through importPartnerBook exactly as 34.3's upload does, with `actor = {kind: human, id: <partner_user_id>, role: partner_admin}`: the import's decision record, `partner_book.import.completed` and `partner_book_imports.actor_id` name the partner user, never `ops_analyst` and never a staff user; the party provisioning, the invitations, the facts and terms rows, the events and the two 33.1 clocks are the import's own work, unchanged. A `partner_ops` or `partner_auditor` session is refused `403 ROLE_REQUIRED{role: partner_admin, act_as: []}` before either file is read (36.1's rule on acts), and the dropzone is not rendered for them.
2. **The partner is the session's; the body never chooses it.** The multipart carries `tape`, `supplement` (optional) and `as_of_date`, and the platform reads nothing else from it: the wrapper builds the import's `partner` from the session's `partner_party_id` — the `parties{servicer}` row's legal name and NMLSR id, with the servicer number and MERS org id the `partners/<id>` entity holds — so a `partner`, `partner_party_id`, `nmlsr_id` or `profile` field in the multipart is dropped before the parse, neither honoured nor an error, and the import attaches to the session partner whatever the field said. Every read of this process carries the same filter (`partner_party_id = session.partner_party_id`); an import id, a loan id or a hold of another partner is `404 NOT_FOUND` (36.1), never `403`.
3. **The profile is registered, not chosen.** The import runs under `m3-v1`, the profile 33.1 registers for the first partner; a client cannot name a profile in V1. When 33.1 registers a second layout, the profile is the one 33.1 records for the partner and still never a form field.
4. **Idempotent as 33.1 is.** The same two files posted again answer `already_loaded` with the earlier import id and write nothing (33.1's `(partner_party_id, tape_sha256, supplement_sha256)` key); the page links the earlier report. A tape with a later `as_of_date` appends a facts row per loan and closes and reopens `loan_terms` per 33.1 rule 2, logging `change ∈ created | updated | unchanged` per loan; whether a tape with an earlier as-of date than the book's is accepted is 33.1's rule, and this process adds none.
5. **The report is 33.1's, in 33.1's shape.** The answer to the POST and to `GET …/imports/:id` is what partnerBookReport returns: `status ∈ loaded | rejected | already_loaded`, rows total and loaded, the exceptions by code with the row number and the servicer loan number, the gap counts, loans created / updated / unchanged, parties created / linked, invitations sent and held, and the loans now on hold (`not_on_latest_tape`); a `rejected` answer lists the headers `m3-v1` requires that the file lacks, exactly as 33.1 emits it. The report carries no homeowner name, e-mail or phone (33.1: never a raw PII row; invitations as counts and hashes). The servicer loan numbers on the report are the partner's own file's: shown in full to `partner_admin` and `partner_ops` on this detail view, as the last four to `partner_auditor` (36.1's mask).
6. **A wrong layout writes nothing of the book.** A header row that does not carry `m3-v1`'s required columns is 33.1's `rejected`: no loan, facts, terms, party, invitation or clock is written or changed, the partner sees the missing headers, and the page keeps the files for a second try; the escalation 33.1 opens for a rejected file goes to `ops_analyst`, not to the partner.
7. **The history.** `GET …/imports` lists the tenant's imports newest first, as listPartnerBookImports returns them: as-of date, status, rows total and loaded, loans created, invitations sent, created at, and who uploaded — the partner user's name from `partner_users` when the actor is one of the tenant's partner users, otherwise "Supermortgage" (a staff or seed actor is never named to the partner). Opening one shows its report and, through 34.3's `book.history`, the per-loan lines with the `change` and, for an updated loan, the facts that differed (34.3 rule 2's before / after: UPB, rate, P&I, next due, status, value) — the same derivation staff see, masked partner-grade.
8. **The status line.** `GET …/status` is partnerBookStatus narrowed to the session partner: `as_of_date` (the latest loaded import's), `next_expected` (the as-of date plus 7 calendar days — the due date of 33.1's `SM_PARTNER_BOOK_TAPE_EXPECTED_7`, read from the clock, never recomputed here), `late` (the clock breached), `on_hold`, `monitored_loans`, `imports`. 36.5's Home tile reads the same line. Before the first import the book is empty and the page says "Upload a tape to open the book."
9. **The holds are visible and untouchable.** `GET …/holds` lists the tenant's loans on hold as holdsOf and 34.3's hold queue find them (the latest facts row older than the partner's latest loaded import and no `keep` resolution in the last 7 days — 33.1 rule 8): loan last four, the homeowner as first name and last initial, state, the last as-of date the loan appeared on, the partner's latest as-of date, held since. No resolve control: `POST /v1/partner/book/loans/:id/resolve` (and any resolve path under `/v1/partner/*`) answers `403 ROLE_REQUIRED{role: ops_analyst, act_as: []}` before any read, whatever the loan id, so the refusal reveals nothing; `book.resolve` stays an `ops_analyst` act on `/ops` (34.3). The hold lifts by itself when the partner's next tape carries the loan. A held loan is off the three buckets (36.3), and its daily review reads `not_now` with reason `not_on_latest_tape` — held out of candidacy, no opportunity, no offer (33.1 rule 8, 33.1-T11): on this surface that is what "absent from the next 33.2 review" means, and the wording is recorded as DELTA-02 in docs/partner-portal/BACKEND-DELTAS.md.
10. **Nothing else is armed, nothing is transferred.** The upload arms only 33.1's clocks (`SM_PARTNER_BOOK_TAPE_EXPECTED_7` satisfied and re-armed from the new as-of date; `SM_PARTNER_BOOK_INVITATION_REMINDER_14` per new invitation) and none of sections 2–19: no ledger, statement, escrow, ACH or delinquency clock on a monitored loan (`LOAN_MONITORED` refuses those commands, 33.1-T9). A tape drop is not a servicing transfer: no Form 629, no Form 101, no RESPA goodbye or hello letter, no custodial account — the partner's incumbent subservicer keeps servicing. The page says "Uploading refreshes monitored facts. It does not transfer servicing."
11. **No message of 36's own.** The import sends 33.1's invitation to each newly provisioned party exactly as it does from `/ops`; the portal composes nothing to a homeowner, offers no re-send, and shows invitations as counts and hashes.
12. **Nothing is computed about a loan here.** Every number on the page is a stored fact, a count of rows or the state of 33.1's clock (34.3 rule 7); a value the platform cannot find is shown as absent, never estimated.

**Worked example A (the demo fixture tape and supplement dropped by the demo partner's partner_admin, as of 2026-09-01).** The answer is `loaded` with `rows_total 12`, `rows_loaded 12`, 12 `loans{status=monitored}`, 12 `partner_book_facts` rows, 12 `loan_terms{source=partner_tape}` rows, a party per loan, an invitation for every party with an e-mail on the supplement (loan 12 has none: `gaps: contact`), 0 on hold, the status line reading as of 2026-09-01, next expected 2026-09-08, not late; the import's decision and `partner_book.import.completed` name the partner user as actor. **12 monitored loans, 0 servicing clocks armed**: no timer of sections 1–19 exists on any of the 12 loans — the only clocks are 33.1's (`SM_PARTNER_BOOK_TAPE_EXPECTED_7` on the global subject, `SM_PARTNER_BOOK_INVITATION_REMINDER_14` per invitation) — and a cashiering, autodraft or escrow command on any of them refuses `LOAN_MONITORED`. The same two files dropped again answer `already_loaded` with the first import id and `partner_book_facts` still holds 12 rows. No money figure is computed here: loan 1's dollar figures are 33.1-T2's and 33.2-T2's, quoted once more by 36.3.

#### Integrations
- None new. The files reach 33.1's `xlsx-reader` and CSV parser through importPartnerBook; 33.1's invitation leaves through 33.1's `edelivery` port (the FAKE in every build stage); no vendor of this process.

#### Outputs and artifacts
- Rows: none of its own — 33.1's rows by the import (`partner_book_imports`, `partner_book_facts`, `partner_book_invitations`, `loans`, `loan_terms`, `properties`, `parties`, `borrowers`, `loan_borrowers`, `notices`, `agent_decisions`), 36.1's `partner_actions`.
- Events: none of its own — 33.1's `partner_book.import.completed`, `partner_book.loan.loaded`, `partner_book.loan.not_on_tape`, `partner_book.account.provisioned`, `partner_book.invitation.sent`, each with the partner actor.
- No notice of its own: the invitation is 33.1's and leaves the import as it does from `/ops`; 36 composes no borrower mail.
- The Book page: the dropzone (`partner_admin` only; not rendered for `partner_ops` or `partner_auditor`), the last import's report, the history table, the holds table (read-only), the status line; the copy "Uploading refreshes monitored facts. It does not transfer servicing." and, on an empty book, "Upload a tape to open the book."

#### AI agent design (AI-first)
`portfolio` agent owns the book on both sides of the door and declares nothing of its own here. End-to-end: the upload is 33.1's own `book.import` (with `account.provision` and `account.invite` inside it) dispatched with the partner user as actor; the report is 33.1's `book.report` and the history 34.3's `book.history`, both read for the session partner; the holds are 33.1 rule 8's read; `book.resolve` is offered to no partner role. Nothing runs unprompted, nothing is proposed for a human, and no partner user can waive, resolve, approve or send. Decision record: none of its own — 33.1's import decision names the partner actor. Guardrails: `LOAN_MONITORED` (33.1: no servicing command on a monitored row), `ROLE_REQUIRED` with `act_as` on the act (34.1 rule 3, reused by 36.1 for the partner roles), `READ_ONLY` on every GET (34.3), `NO_DESTINATION` (34.3: invitations as counts and hashes), `NO_PII_IN_LOG` (34.1, reused by 36.1's `partner_actions`), and 36.1's tenant rule (the partner is the session's; another tenant's row is 404). Escalations: none of its own — a rejected file and a late tape are 33.1's `ops_analyst` escalations; `officer` for nothing, because no money field moves here.

#### Edge cases and failure modes
- A `partner_ops` or `partner_auditor` posts the files → `403 ROLE_REQUIRED{role: partner_admin, act_as: []}` before either file is read; nothing written; the dropzone was never rendered for them.
- The multipart names a partner, an NMLSR id or a profile → the field is dropped; the import attaches to the session partner under `m3-v1`; the answer does not mention the field.
- The header row is not `m3-v1`'s → 33.1's `rejected` with the missing headers listed; nothing of the book written; the page keeps the files for a second try; 33.1's escalation goes to `ops_analyst`.
- The same files dropped twice → `already_loaded` with the earlier import id; no second history row; the facts count is unchanged.
- A later tape drops a loan → on hold, listed under Holds with its last as-of date; not resolvable here; the next tape that carries it lifts the hold; an `ops_analyst` resolves it on `/ops` (34.3).
- Two tapes on one day → two imports, two as-of rows; the later one is the book (34.3).
- The tape is late → the status line reads late; the escalation is 33.1's to `ops_analyst`; the partner sees "next expected <date>, late" and no other consequence; the book keeps being reviewed on its last facts (33.1).
- The session expires during an upload → 401 (36.1's session expiry); nothing written, because the import is one unit of work.
- A partner with no import yet → an empty history, a status line without an as-of date, "Upload a tape to open the book."
- A resolve path is called with any loan id → `403 ROLE_REQUIRED{role: ops_analyst, act_as: []}` before any read, the same answer for the tenant's own loan and for another tenant's, so the refusal reveals nothing.

#### Audit and evidence
What an examiner is shown: the import row with both file hashes, its report and `actor_id` naming the partner user; 33.1's decision record and `partner_book.import.completed` with the partner actor; the history with who uploaded what; the holds with the last as-of each loan appeared on and, once resolved on `/ops`, 33.1's resolution with its reason and staff actor; 36.1's action-log rows for the upload and for every read (ids, role, result, no PII); the timer history of 33.1's next-tape clock behind the status line. Exported through 34.4's evidence pack; the partner's own export is the daily report (36.5).

### Open questions / decisions
1. Should the partner's profile be a per-partner setting rather than the constant `m3-v1`? **Default: `m3-v1` in V1; when a second layout arrives, 33.1 records the partner's profile and this process reads it; a form field never chooses it.**
2. Should a partner see the exceptions' servicer loan numbers in full on the report? **Default: yes for `partner_admin` and `partner_ops` — the report is a detail view of the partner's own file — and the last four for `partner_auditor`; never a homeowner's name, e-mail or phone.**
3. Should a `partner_admin` be able to ask for a hold to be resolved from the portal (a request, not a resolution)? **Default: no control in V1 — the partner's next tape carries the loan, or the partner asks ops out of band; `book.resolve` stays an `ops_analyst` act on `/ops`.**
4. Should the tape be accepted by SFTP or API pull as well as by upload? **Default: upload only in this process (34.3's own default); a pull is a later 33.1 extension that lands in the same `book.import`.**
