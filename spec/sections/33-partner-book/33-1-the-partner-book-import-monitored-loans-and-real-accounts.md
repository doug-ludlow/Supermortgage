# 33.1 — The partner book import: the tape and the supplement become monitored loans and real accounts

| Attribute | Value |
|---|---|
| Section | 33 — The partner book: monitored loans, real accounts and refinance readiness |
| Automation class | a — the operator uploads two files; the `portfolio` agent loads, provisions and invites; no human touches a row |
| Capacity | Platform (Supermortgage holds the account and the relationship); the partner stays servicer of record of every monitored loan and is the lender of the refinance program |
| Trigger & frequency | On upload of a partner tape (and its e-mail/phone supplement); re-uploads as new as-of snapshots; the first sign-in of each homeowner |
| Governing source | GLBA §1016.13 (the partner's data used for the partner's program); CAN-SPAM 15 U.S.C. §7702(17) (the invitation is a transactional/relationship message about an existing account); TCPA 47 U.S.C. §227(b) (a text only with the partner's consent evidence); FCRA §604 (no consumer report is obtained on import); 32.14 rule 8 and 32.2 (accounts, doors, levels); 20.1 rules 6–8 (the program is the partner's; the universe is investor-blind; selection inputs are the allowlist) |
| Key deadlines | The invitation on the day of import; one reminder at 14 days if the account is not yet activated; the next tape expected 7 calendar days after the last as-of date |
| Timers | `SM_PARTNER_BOOK_INVITATION_REMINDER_14`, `SM_PARTNER_BOOK_TAPE_EXPECTED_7` |

### Blueprint row
The partner sends its book as a spreadsheet in its own layout plus a second file with each borrower's e-mail and phone. Today nothing can take it: the only intake is 1.1's Fannie Mae transfer tape (68 fixed columns, a hard-fail gate that refuses every loan without a Fannie Mae loan number, a TIN, late-charge terms and a custody record), boarded loans get no party and no contact, and no homeowner from a tape can sign in. The product needs the opposite: every person on the tape is a real account the day the file lands, the loans are watched (not serviced) and the daily agents work them. This process is that intake: a partner tape profile, monitored loans with the partner's facts kept whole, a party with the partner's contact for every borrower, an invitation, and the first sign-in landing on the loan.

### Verified requirement (as of 2026-09-14)
**Monitored, not serviced.** A loan loaded here carries `loans.status = monitored`: it is never selected by the 2.x cashiering sweep (`origination_application_id IS NULL` and status ≠ `active`), the 11.x delinquency sweep (no `loan_installments` rows are projected), any notice run or any timer of sections 1–19 (none arms on `partner_book.*` events); no ledger opening set is posted. The partner's facts are the record: balances, rates, payments, next due, pay string, status — refreshed only by the partner's next upload. A monitored loan enters the refinance universe (33.2) and nothing else. **[PARTIALLY VERIFIED — the servicing sweeps' filters are read from source (src/runtime/servicing.ts, src/runtime/delinquency.ts, refi-daily.ts); the timer registry's section ≥ 20 arming rule is the kernel's.]**

**The account is the party (32.2; 32.14 rule 8).** A borrower is a `parties{borrower}` row whose `contact` carries the e-mail and phone; the code door resolves a verified destination to the oldest party carrying it and opens an L1 session; the loan is the party's subject through `borrowers.party_id → loan_borrowers` (02 §6). Nothing about that changes here: the import writes exactly those rows, so the homeowner's first sign-in is the platform's own door. A password is optional afterwards through the account door (an e-mail on file → a code → the password on the same party).

**The invitation is a relationship message (CAN-SPAM §7702(17)(A)(v)); a text needs consent (TCPA §227(b)(1)(A)).** The e-mail tells the homeowner that their servicer now provides an account here for their existing loan and how to sign in; it carries the partner's name, the loan's last four, no rate, no offer and no figure. It goes to every borrower with an e-mail on the supplement. The SMS variant goes only when the partner's file carries TCPA consent evidence for the number (the boarding tape's `consents.tcpa_voice_evidence` field or a `consents{kind=tcpa_sms}` row); otherwise no text. Refinance offers are never in the invitation — they are 20.2's touches with 20.2's gates.

**No report is obtained (FCRA §604(a)).** The import reads the partner's FICO from the tape as a fact of the partner's file (`representative_score`, `score_source = partner_file`, pricing input only — 20.1 rule 8 keeps it out of selection); it never orders a consumer report. **[UNVERIFIED — whether the partner's tape FICO may be used for LLPA pricing of a prescreened offer without a firm offer of credit is counsel's question; default: it prices the benefit shown to the borrower after the borrower's own Yes, exactly as the origination-file score does today.]**

**Discrepancies vs blueprint**: (1) The 1.1 transfer gate is not run on a monitored book — its hard rules assert a Fannie Mae servicing transfer this is not; the tape profile records what is missing (TIN, DOB, mailing address, co-borrower, consents) as gaps on the import report, never as refusals. (2) 32.14 rule 8 assumed a letter and a code to the number on file; there is no letter — the destination on file is the login. (3) 32.11 §1 forbids a proactive "we are watching" line; the first-sign-in greeting names the loan, the servicer and what the account is for, and says nothing about rates or offers.

### Operational prerequisites
- The partner's legal name, NMLSR id, servicer number and MERS org id (the `parties{servicer}` row the loans point at; the `partners/<id>` entity; the `partner_programs` row through 20.1 `loadUniverse{op=register_program}`, product owner `partner`).
- The partner's tape layout as a profile (`m3-v1` for the first partner: the 118 columns in `src/domain/partner-book/profiles/m3-v1.ts`) and the supplement layout (`servicer_loan_number, borrower_email, borrower_phone`; a `borrower_name` column when present must match the tape's).
- An operator token for `POST /v1/partner-book/imports`; the FAKE e-mail/SMS port in every build stage; production PII handling per DEPLOY.md before a real file is loaded anywhere but production.

### Build spec
#### Inputs and triggers
- `POST /v1/partner-book/imports` (operator bearer; JSON `{partner: {legal_name, nmlsr_id, servicer_number?, mers_org_id?}, as_of_date, profile: "m3-v1", tape: {filename, content_base64}, supplement?: {filename, content_base64}}`; `.xlsx` or `.csv` for either file; the same body as multipart fields `partner`, `as_of_date`, `profile`, `tape`, `supplement`) → the `portfolio` agent's `book.import`.
- `partner_book.import.completed{import_id, partner_id, as_of_date, rows_total, rows_loaded, rows_exception, loans_created, loans_updated, parties_created, parties_linked, invitations_sent, gaps}` (global; the import's own record).
- `partner_book.loan.loaded{loan_id, servicer_loan_number, as_of_date, change ∈ created|updated|unchanged, origination}` per loan (loan-scoped; `origination: true` on every 33.x payload so the section's own clocks arm).
- `partner_book.account.provisioned{party_id, loan_id, borrower_id, channels, linked_existing_party, origination}`; `partner_book.invitation.sent{party_id, loan_id, channel, notice_id, sent_at, origination}`; `partner_book.account.activated{party_id, loan_id, session_id, activated_at, origination}` (the session hook on the first session of a party with a monitored loan).
- `partner_book.loan.not_on_tape{loan_id, servicer_loan_number, as_of_date, origination}` (loan-scoped) and `partner_book.loan.resolved{loan_id, resolution, reason, origination}` (loan-scoped; `book.resolve`); `partner_book.tape.late{partner_id, last_as_of_date, expected_by}` (global; the breach of `SM_PARTNER_BOOK_TAPE_EXPECTED_7`).
- The demo seed (`main.ts seed-demo`) imports the fixture book so every deployed demo carries a partner book.

#### Data model
New tables (append-only; PII columns as marked; retention `servicing_file`):
- **`partner_book_imports`** (new; append-only): `id uuid pk`, `partner_party_id` → `parties`, `as_of_date date`, `profile text`, `tape_sha256 text`, `supplement_sha256 text`, `rows_total int`, `rows_loaded int`, `rows_exception int`, `loans_created int`, `loans_updated int`, `parties_created int`, `parties_linked int`, `invitations_sent int`, `report jsonb` (the per-row exceptions and the gaps, never a raw PII row), `actor_id text`, `created_at`. Idempotent on `(partner_party_id, tape_sha256, supplement_sha256)`: the same files land once.
- **`partner_book_facts`** (new; append-only; pii): `id uuid pk`, `import_id` → `partner_book_imports`, `loan_id` → `loans`, `partner_party_id` → `parties`, `as_of_date date`, `facts jsonb` (every mapped column of the profile, typed: money as decimal-string cents, dates as ISO, flags as booleans), `raw jsonb` (every unmapped column by header), `created_at`. The latest row per loan is the record 33.2 and the borrower record read.
- **`partner_book_invitations`** (new; append-only; pii): `id uuid pk`, `import_id`, `party_id` → `parties`, `loan_id` → `loans`, `channel text` ∈ {email, sms}, `destination_hash text` (sha256 of the normalized destination; never the destination), `notice_id uuid`, `message_id text`, `sent_at timestamptz`, `kind text` ∈ {invitation, reminder}, `created_at`.
- Baseline tables written: `parties` (+ one `servicer` row per partner; one `borrower` row per homeowner with `contact {email, phone}`), `properties`, `loans` (`status = monitored`; `fnma_loan_number` null — the column becomes nullable and its check accepts `status = monitored`; `servicer_loan_number` = the partner's number; `min` = the MERS id when it is an 18-digit Luhn-valid MIN, else null; `partner_party_id`, `property_id`, `instrument_date`, `origination_date`, `original_upb_cents`, `original_term_months`, `first_payment_date`, `maturity_date`, `principal_residence`), `loan_terms` (`source = partner_tape`, `effective_from = as_of_date`, the prior row closed with `effective_to` on a re-upload; `note_rate_bps`, `pi_cents`, `escrow_payment_cents`, `escrowed`, `amortization`, `maturity_date`, `remaining_term_months`, the ARM fields; `remittance_type` from the tape's agency/remittance text when it reduces to A/A, S/A or S/S, else A/A — investor data the refinance view never selects), `borrowers` (`legal_name`, `party_id`; `tin_last4` and `date_of_birth` when the supplement carries them), `loan_borrowers`, `loan_events` (the events above), `agent_decisions` (`book.import`, `account.provision`, `account.invite`), `notices`/`notice_deliveries` (the invitation), `entity_records` (`partners/<id>`, `partner_programs`, the loan's `refi_universe` row written by 33.2's projection), `timers` (`SM_PARTNER_BOOK_INVITATION_REMINDER_14`). The `loan_status` enum gains `monitored`; `v_refi_universe` includes `monitored` loans (33.2 reads their facts from `partner_book_facts`, never from ledger or installments).

#### State machine
Per import (`partner_book_imports`): `received → loaded` (one transaction: every row parsed, every loan and party written, the report stored) or `rejected` (the file is not the profile: the header row does not carry the profile's required columns — nothing is written). Per loan (`loans.status`): `monitored` from the first load; `monitored —(a refinance funds here, 30.x)→ paid_off` on the monitored loan and `active` on the new one; `monitored —(the partner's upload marks it paid/transferred)→ paid_off | transferred_out` with the tape's status as the reason; a loan absent from a later tape stays `monitored` on hold (`not_on_latest_tape`) until the next tape carries it or `book.resolve` closes it (rule 8). Per homeowner: `invited —(first session)→ activated`; a reminder once at 14 days while `invited`. No human performs a transition; the operator only uploads.

#### Timers and gates
| Timer code | Kind | Trigger event | Anchor | Offset & unit | Satisfied by | Breach action |
|---|---|---|---|---|---|---|
| `SM_PARTNER_BOOK_INVITATION_REMINDER_14` | deadline | `partner_book.invitation.sent{kind=invitation}` | `sent_at` | +14 calendar_days | `partner_book.account.activated` | sev 3 → `portfolio` (one reminder on the same channel, then the clock closes) |
| `SM_PARTNER_BOOK_TAPE_EXPECTED_7` | recurring | `partner_book.import.completed` | `as_of_date` | +7 calendar_days | `partner_book.import.completed` | sev 3 → `ops_analyst` (the partner's next tape is late; the book is stale) |

Jurisdiction overrides: none.

#### Business rules and calculations
1. **The profile maps; nothing is refused for being missing.** `m3-v1` maps the first partner's 118 headers onto typed facts (identifiers, borrower name, property, balances, rates, payments, dates, pay strings, scores, values, LTVs, occupancy, product and ARM terms, cash-flow months, foreclosure and bankruptcy fields, servicing status, PMI, property details, advances and escrow balances, modification and prepayment flags, MBA status, DTI, agency/remittance). Money cells become decimal-string cents (half-up to the cent), dates become ISO dates (Excel serials converted), Y/N and 1/0 become booleans; a cell that cannot be read is recorded as a row exception naming the column and the row keeps every other fact. Headers the profile does not know are kept verbatim under `raw`. A row is skipped only when it has no servicer loan number, no property state, or no readable balance and rate — and the skip is on the report. The supplement joins on the servicer loan number; a supplement row with no tape row is a report exception; a tape row with no supplement row is loaded without contact (`gaps: contact`).
2. **The loan is monitored, and the record of it is the partner's.** The loans/loan_terms/properties rows carry what the platform's readers need (the record's numbers, 33.2's universe); the whole typed row lives in `partner_book_facts`. A re-upload with a later `as_of_date` appends a facts row, closes the open `loan_terms` row and opens the new one, and logs `partner_book.loan.loaded{change=updated}`; a row whose typed facts are unchanged logs `change=unchanged` and writes no terms. The tape's investor columns (agency and remittance type, investor net rate, servicer-retained rate, servicer name, MERS id) stay in `facts`/`raw` and never reach the refinance universe (20.1 rule 7: `INVESTOR_FIELDS`).
3. **One homeowner, one party, real from the first load.** For every loan the primary borrower gets a `parties{borrower}` row (`legal_name` = the tape's name; `contact.email` and `contact.phone` normalized from the supplement), a `borrowers` row with `party_id` set and a `loan_borrowers` row. If a borrower party already carries the normalized e-mail **and** the same normalized name (last name and first initial), the loan is linked to that party (`linked_existing_party = true`) — the person is already here; the same e-mail on a party with another name is a report exception (`contact_conflict`) and the loan gets its own party without that e-mail, because a party is never linked on an unverified e-mail (32.14). Two borrowers on one loan with the same e-mail (a household address) are two parties; the second keeps the phone only. A homeowner who later verifies an e-mail that is also on a homegrown party is merged onto that party by the door's own rule (the verified code proves possession).
4. **The invitation.** Once per provisioned party, `account.invite` renders `NTC_SM_PARTNER_BOOK_INVITATION` by e-mail (channel policy `electronic_ok_without_esign`: the notice is about the account, not a disclosure) with the partner's name, the loan's last four, the sign-in address and the sentence that a code will be sent to this e-mail; by SMS only under the consent rule above. `partner_book.invitation.sent` arms the reminder; the breach sends one reminder (`kind = reminder`) and closes the clock; `partner_book.account.activated` satisfies it. A party with no e-mail and no textable phone is `gaps: contact` on the report and invited when a later supplement supplies one.
5. **The first sign-in lands on the loan.** The party's subjects resolve the monitored loan (02 §6); the session hook logs `partner_book.account.activated` once, starts no organic lead and no organic application (3-entry's hook stands down when every subject is a monitored loan), and — through the code door as through the account door — runs the first turn: the assistant greets by name, says the loan with the partner is on the record, that the partner keeps servicing it and that this is where the platform will talk to them about it. No rate, no offer, no figure in that turn (32.11 §1; the guard's provenance rule).
6. **What the record shows for a monitored loan.** Badge `Monitored` with the one-liner naming the servicer; `numbers` from the latest facts (UPB, note rate, P&I, T&I, next due date, last payment date) — never from ledger or statements; the property; the partner as the servicer of record with its contact; no autopay, escrow, payment or hardship commands (each refuses `LOAN_MONITORED` with the servicer's name; the command surface lists them as unavailable); the rate-watch block and any offer as 32.11 renders them once 33.2 writes them. L2 for a monitored party is SSN last four plus DOB when the supplement carried them, else the identity step of a refinance application (33.3) — the L3 scan supersedes L2.
7. **The demo book.** The fixture is a deterministic 12-loan book in the `m3-v1` layout (10 owner-occupied, 1 second home, 1 investment; 9 current, 1 thirty days late, 1 in an active bankruptcy, 1 with a foreclosure referral; one with no supplement row; one whose e-mail belongs to an existing homegrown party with the same name) with a matching supplement; the seed imports it under the demo partner so the demo walk can sign a homeowner in.
8. **Regular tapes.** The partner sends its tape on a cadence (weekly for the first partner); `partner_book.import.completed` arms `SM_PARTNER_BOOK_TAPE_EXPECTED_7` on the global subject from the tape's as-of date and the next import satisfies and re-arms it; a breach is an `ops_analyst` escalation (`partner_book.tape.late{partner_id, last_as_of_date, expected_by}`) and the console shows "book as of <date>, next expected <date>". A loan on the book that is **absent from a later full tape** of the same partner is never silently closed: the import logs `partner_book.loan.not_on_tape{loan_id, servicer_loan_number, as_of_date, origination}`, the report counts it under `not_on_latest_tape`, the loan keeps `status = monitored` and is held out of the daily review (33.2 `not_now`, reason `not_on_latest_tape`) until the partner's next tape carries it again (the hold lifts) or an operator resolves it with `book.resolve{loan_id, resolution ∈ paid_off | transferred_out | keep, reason}` (an `ops_analyst` action; `paid_off`/`transferred_out` move `loans.status` and log `partner_book.loan.resolved`; `keep` lifts the hold for 7 days). A party provisioned with `gaps: contact` whose later supplement supplies an e-mail (or a textable phone with consent evidence) is invited at that import (`account.invite` runs for it; the reminder clock arms then).

**Worked example A (loan 1 of the fixture as it lands).** Servicer loan number `NL-100001`, Maria Garcia, 1200 W Maple Ave, Phoenix, AZ 85013, Maricopa; original principal $450,000.00 closed 2024-09-20, first payment 2024-11-01, 7.250% fixed over 360 months; the tape's interest-bearing UPB after the 2026-09-01 payment (23 payments) is the scheduled balance: 450,000.00 × (1.006041667)^23 − 3,069.79 × ((1.006041667)^23 − 1) ÷ 0.006041667 → **$441,366.13**; the current P&I 450,000.00 × 0.006041667 ÷ (1 − 1.006041667^−360) = 3,069.7889 → **$3,069.79**; T&I **$612.50**; Current FMV **$605,000.00** (2026-08-31) and Most Recent BPO $610,000.00 (2026-06-15); Current FICO 748. The record's numbers after import read UPB $441,366.13, note rate 7.250%, P&I $3,069.79, next payment due 2026-10-01; `loan_terms.note_rate_bps = 72500`, `pi_cents = 306979`, `escrow_payment_cents = 61250`, `remaining_term_months = 337`.

#### Integrations
- **`xlsx-reader`** (in-repo, dependency-free: the zip's central directory, `node:zlib` inflateRawSync per entry, the shared-strings and sheet XML; serial dates and numbers to strings). CSV through the boarding codec's RFC-4180 parser. No vendor.
- **`edelivery`** (outbound e-mail/SMS; the FAKE `FakeEdelivery` in every build stage; idempotency `partner_book:<import>:<party>:<channel>`; a bounce is recorded on the invitation row and the party is `gaps: contact_bounced`).
- **20.1** `loadUniverse{op=register_program}` for a partner without a program; **32.1** `create_deep_link` is not used (the invitation links to the sign-in page with the e-mail prefilled; the code proves possession).

#### Outputs and artifacts
- Rows: `partner_book_imports`, `partner_book_facts`, `partner_book_invitations`, `parties`, `properties`, `loans{status=monitored}`, `loan_terms{source=partner_tape}`, `borrowers`, `loan_borrowers`, `notices` (the invitation), `agent_decisions`.
- Events: `partner_book.import.completed`, `partner_book.loan.loaded`, `partner_book.account.provisioned`, `partner_book.invitation.sent`, `partner_book.account.activated`.
- Notice `NTC_SM_PARTNER_BOOK_INVITATION` (e-mail and SMS variants; content checklist: the partner's legal name as servicer, the loan's last four, the sign-in address, "we will send a code to this e-mail", no rate, no offer, no figure, the platform's postal address and the one-line reply-to-stop for the SMS).
- The import report (`partner_book_imports.report`): per-row exceptions `{row, servicer_loan_number, code ∈ unreadable_cell|no_loan_number|no_state|no_balance_or_rate|supplement_orphan|contact_conflict, column?}` and the gap counts `{contact, tin, dob, mailing_address, coborrower, consents, not_on_latest_tape}`; the operator's console view lists it.

#### AI agent design (AI-first)
`portfolio` agent (tools: `book.import`, `account.provision`, `account.invite`, `book.report`, `book.resolve`). End-to-end: `book.import` parses both files under the named profile, writes the partner rows, and runs `account.provision` per loan and `account.invite` per newly provisioned party inside one unit of work; `book.report` reads an import's report and the book's counts for the console; `book.resolve` is the operator's resolution of a loan absent from the latest tape (rule 8). Decision record per import `{import_id, profile, rows_total, rows_loaded, rows_exception, gaps, rule_set_version: partner_book.m3.v1, model_version: deterministic, prompt_version: 33.1-v1, confidence: 1, rationale}` and one per provisioned party (linked or created, the contact channels). Guardrails: never a consumer report, never a payment, statement, escrow or delinquency action on a monitored loan (`LOAN_MONITORED`), never an investor column outside `facts`/`raw`, never a party linked on an unverified e-mail alone, never an SMS without consent evidence (`NO_TCPA_EVIDENCE`), never a destination in a log line or a report (hashes only). Escalations: `ops_analyst` for a rejected file (wrong layout) and for `contact_conflict` rows; `officer` for nothing — no money field moves here.

#### Edge cases and failure modes
- The header row is not the profile's (fewer than the required columns) → `rejected`, nothing written, the operator sees which columns were expected.
- A cell overflows (a rate above 25%, a UPB above the original principal by more than 10%) → loaded with a row exception `implausible_value` naming the column; the refinance review (33.2) suppresses the loan while the exception stands.
- The same tape uploaded twice → `already_loaded` with the earlier import id; a later as-of → updated rows.
- A servicer loan number appears twice in one tape → the second row is a `duplicate_row` exception.
- The supplement's e-mail is malformed or the phone is not E.164-normalizable → the channel is dropped, `gaps: contact` when both are.
- The MERS id is not a valid MIN → `min` null, the id kept in `facts`.
- A homeowner signs in by a phone code before any e-mail → the same party (the phone is on its contact); an e-mail on file for another party → the door's `PARTY_SCOPE` refusal stands.
- The partner marks a loan paid or transferred on a later tape → `paid_off` / `transferred_out` with the tape's status in the event; the record's badge follows; the party keeps the account.
- A loan absent from a later tape → on hold (`not_on_latest_tape`), reviewed no more until it returns or an operator resolves it; the party keeps the account and the record.
- The partner's tape is late → `SM_PARTNER_BOOK_TAPE_EXPECTED_7` breaches, ops is escalated once, the book keeps being reviewed on its last facts (33.2 marks a value older than 24 months `not_now` on its own).

#### Audit and evidence
What an examiner is shown: the import row with both file hashes and the report; per loan the facts rows by as-of date and the `loan_terms` history; per homeowner the provisioning decision (created or linked, channels as hashes), the invitation rows with delivery status, the activation event and session; the timer history of the reminder; the notice's rendered text and its content checklist. Exported through the console's partner-book view and the standard evidence pack (events, decisions, notices).

### Open questions / decisions
1. Should a party be linked to an existing homegrown party on name plus e-mail at import, or only on a verified code? **Default: name plus normalized e-mail links at import; a conflicting name never does; the verified code merges the rest.**
2. Should a tape without any consent evidence send SMS invitations? **Default: no — e-mail only until the partner's consent evidence arrives.**
3. Should the reminder go more than once? **Default: once at 14 days; the daily agents' offers carry the relationship after that.**
