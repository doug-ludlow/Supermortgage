### Blueprint row
The hosted runtime runs one scheduled pass a minute (`Runtime.sweep`, src/runtime/app.ts:254-308; the `sweep` job, src/runtime/main.ts:58-70; Cloud Scheduler `* * * * *` with a 180 s attempt deadline, infra/terraform/scheduler.tf:8,11, against a 300 s job, run.tf:347-348). Its body is the 20.1 refinance run, the 33.2 review, the 33.3 readiness pass, the 34.3 daily reports, the 34.4 kill-switch expiry, the FAKE reviewers, the breach pass and an outbox count (app.ts:254-307); the borrower flows' `tick` adds 2.1 posting, 2.7 late charges and 2.3 amount-change checks for loans with `origination_application_id` only (src/runtime/servicing.ts:133) and the delinquency counter job for loans that have `loan_installments` rows (src/runtime/delinquency.ts:40-43). Nothing schedules a periodic statement, a Form 1098, an escrow analysis, a LAR period, a remittance, a custodial reconciliation, a Metro 2 snapshot, an ARM or MI change: `sendPeriodicStatement` and `furnishForm1098` (servicing.ts:205, :249) have only test callers, and 7.1 and 8.1 register no bus tool at all (spec/registry/manifest.json: `7.1 tools: []`, `8.1 tools: []`). The pass has no lease, no once-per-day gate, no batching of the due timers (`timers.due` has no `LIMIT` and no locking clause, src/infra/db/timers.ts:52-54) and no per-unit retry; a second overlapping execution can double-breach and double-open. This process is the batch architecture the gap assessment names as blocking ("Batch / cycle architecture", evidence servicing.ts:205,249, app.ts:246-300, main.ts:58-63) and, of the concurrency gap it names as major (unit-of-work.ts:79-122, timers.ts:34,52-53, scheduler.tf:8,11, run.tf:347-348), only the paged breach pass and the planner lock — the sweep lease and the per-loan lock that close that gap are 35.1's (README, gap table): a planner that runs once at a time and plans idempotently, a `jobs` table with wall-clock leases claimed `SKIP LOCKED`, a `cycle_runs` row per (cycle, period) whose last unit elects the receipt, one bus tool `cycles.run_unit` that carries every unit — including the §7/§8 units that have no spec tool — through the same unit of work, decision record and guardrails as every other command, a code registry of every cycle with its receipt event and the section timer it serves, a bounded retry policy of its own, and the demo clock's advance running the planner and the units inline per crossed day. Today an operator invokes the compute tools by hand with hand-fed state; after this process a loan's cycles run because the calendar says so, and the receipt proves it.

### Verified requirement (as of 2026-09-15)
**The sweep is many transactions with no lease of its own (src/runtime/app.ts:254-308; src/runtime/main.ts:58-70).** Each daily pass commits through the command bus in its own transactions; the breach pass is one `db.tx` over every due timer (`this.uow.timers.due(nowIso)`, :278; `TimerEngine.restore` + `evaluate`, :282-293; one escalation per breach, :288-292). 35.1 rule 12 adds the execution lease (`pg_try_advisory_lock(35_001)` on a dedicated client) and the `FOR UPDATE SKIP LOCKED` clause on the due query; this process adds the paging and the planner. **VERIFIED** at HEAD 5e34fe6.

**A session-level advisory lock dies with its connection (PostgreSQL 16 manual §13.3.5; src/infra/db/test-lock.ts:14-20).** `pg_advisory_lock` / `pg_try_advisory_lock` on a dedicated `pg.Client` is held until unlocked or the session ends; the tree's precedent takes it in `test.before` and releases it in `test.after` on its own client, outside the pool of four (src/infra/db/client.ts:35). `FOR UPDATE SKIP LOCKED` lets concurrent claimers take disjoint rows (SELECT "The Locking Clause"). **[PARTIALLY VERIFIED — the manual is cited from memory; the in-tree precedent and the pool size are verified at HEAD.]**

**The engine arms only on a trigger event and keeps one global recurring instance (src/kernel/timers/engine.ts:159-183).** `onEvent` satisfies then arms; a def with `subjectOverride: "global"` and `kindNorm === "recurring"` is skipped while an armed global instance exists (:180-181). A registered cycle that has never run therefore has no clock to breach — its absence is a registry finding, not a timer's. The offset grammar accepts `hours` and `minutes` beside the day units (src/kernel/timers/offset.ts `UNIT_ALIASES`). **VERIFIED.**

**The outbox's retry policy is not this process's (src/infra/integrations/outbox.ts:76-78,125-155).** `DEFAULT_RETRY = { maxAttempts: 5, baseDelayMs: 60_000, maxDelayMs: 30 * 60_000 }` with exponential backoff and `dead` after the fifth attempt; 35.1 rule 11 drains the outbox every sweep with that policy unchanged. Jobs here carry `JOB_RETRY` (rule 7), a distinct constant, so a dead unit and a dead message are never confused. **VERIFIED.**

**The demo clock steps per crossed day and runs the sweep minute inline (src/runtime/demo-clock.ts:56,62,84-88,117-126,251-261,266).** Each step writes its `demo_clock` row before its passes (:117-121), runs `flows.tick`, `settle`, then `Runtime.sweep(step.at)` (:251-261) within a 240 s budget (:62); one advance at a time per instance (:125-126); the sweep job reads the offset once at start (main.ts:54-55) while `serve` instances follow the table every second (main.ts:110-111). A planner that read `clock.now()` without `refresh()` on the sweep job would plan a day the API instance has already advanced past. **VERIFIED.**

**Statements and 1098s have runners but no scheduler (src/runtime/servicing.ts:173,205,249).** `sendPeriodicStatement(rt, loanId, { cycle_due_date, statement_date?, cycle?, now? })` builds `LoanCashState` server-side, runs `StatementCycleService` under the loan's unit of work and returns `{ notice_id, channel, mailed_at, statement_date, events }`; `furnishForm1098(rt, loanId, { tax_year, furnished_on? })` runs the 7.1-A / 7.4 rule-11 path. Neither is reachable from `Runtime.execute` (app.ts:180-183 requires a registered `(process, name)` pair; `7.1` and `8.1` register none). The 8.1 snapshot builder emits `credit.cycle.snapshot_completed` from `src/domain/credit-reporting/ops.ts:214-218`; the 5.1 batch builder and `SequenceAllocator` are `src/domain/investor/batch.ts:1-25`. **VERIFIED.**

**6.3's Form 496 waits on two closes (spec/sections/06-custodial-account-management/6-3-*.md:50,72,79).** "Monthly: `ledger.period.closed` (month-end cut-off), `fnma.reporting_period.closed` (BD2 17:00 ET) … → `custodial.reconciliation.monthly_started`"; the machine composes only on `ledger.period.closed` ∧ the month-end statement and drafts only once the LSDU period is closed. #### State machine
Per job (`jobs.status`): `blocked` —(every `depends_on` receipt or event present; planner)→ `queued` —(claim `FOR UPDATE SKIP LOCKED`; executor)→ `running` —(unit committed)→ `done` (terminal) | —(unit threw, `attempts < max_attempts`)→ `failed` —(`run_after` reached; planner)→ `queued` | —(unit threw, `attempts = max_attempts`, or an `unavailable`-class failure)→ `dead` —(`jobs.requeue{op: requeue}`, `ops_analyst`)→ `queued` | —(`jobs.requeue{op: abandon}`, `ops_analyst`)→ `abandoned` (terminal); `running` —(`lease_until < now()`; planner)→ `queued` (the attempt counted, `job.lease.expired`); `blocked` | `queued` —(run cancelled)→ `skipped` (terminal). Per run (`cycle_runs.status`): `planned` —(first claim)→ `running` —(`units_done + units_dead + units_skipped = units_total` and `units_dead = 0`)→ `completed` (terminal; the receipt); a run with a dead unit stays `running` until the unit is requeued and done or abandoned (an abandoned unit counts as `skipped` toward the total, and the receipt records `units_dead > 0`); `planned` | `running` —(`cycles.registry{op: pause}` then `cycle.run.cancelled`, `ops_analyst`)→ `cancelled` (terminal). Per registry row: `active` ⇄ `paused` (`ops_analyst` with a reason, logged) → `retired` (a code removed from cycles.ts; the planner never plans it again, its history stays). Who: the planner and the executor are `ops-steward` acting as `{kind: "agent", id: "ops-steward"}`; every unit runs as the owning section's agent (the registry row's `owner_agent`), so the decision record and the events name `cashiering`, `disclosures`, `investor-reporting`, `custodial-recon`, `credit-reporting`, `escrow`, `default-collections` — never `ops-steward`; requeue, abandon, pause and cancel are `ops_analyst` acts.

Jurisdiction overrides: none. `SM_CYCLE_PLANNER_DAILY` is a recurring global clock and takes a cited `subject: "global"` override in `src/domain/operations-runtime/timers-35-3.ts` on the `timers-33-2.ts` precedent (src/domain/partner-book/timers-33-2.ts:17-19; the engine keeps one armed instance per global recurring code, src/kernel/timers/engine.ts:180-181), with the hour in the override (`+1 calendar_days, 23:59 ET` — the day's last minute, since the planner runs every minute and the clock asks only that some pass completed today). `SM_CYCLE_RUN_STALLED_1D` is armed per run on the `cycle_run` aggregate (the batch-level pattern of unit-of-work.ts:86-87: a global command hydrates `timers.openGlobal()`, so the receipt's global command satisfies it); the same override file cancels it on `cycle.run.cancelled` with the citation "state machine: a cancelled run has nothing left to complete". `SM_JOB_DEAD_2H` is per job on the `job` aggregate; the override file maps the breach role from the registry row's `escalation_role` (the registry's breach column names the default; the evaluator reads the row).

#### Business rules and calculations
1. **One planner at a time, and it never blocks the sweep.** `cycles.plan` opens a dedicated `pg.Client` (the test-lock.ts:14-20 pattern), takes `pg_try_advisory_lock(35_003)` and, if refused, appends `cycles.plan.skipped{holder}` and returns — the sweep's other passes run regardless. The lock is session-level so it dies with the client: a planner killed mid-pass (the job's 300 s timeout) leaves nothing locked, and the next minute's pass plans the same window idempotently (rule 3). The lock key is distinct from 35.1's sweep lease (`35_001`) because the demo advance calls the planner from a `serve` instance that holds no sweep lease (rule 10). Guardrail `LEASE_DIES_WITH_SESSION` (no table row is ever the lock; `sweep_runs`/`cycle_runs` record, they never guard).
2. **The registry is code; the table is its projection.** `src/domain/operations-runtime/cycles.ts` exports `CYCLES: readonly CycleDef[]` with, per cycle, `{ cycle_code, owner_process, owner_agent, unit_scope, schedule, period_grammar, selector, runner, receipt_event, depends_on, serves_timer, escalation_role, expected_by }` where `selector(db, window) → Unit[]` is a SQL read over typed rows (never `entity_records`) and `runner(rt, unit, ctx)` invokes the owning section's command; the planner upserts each def into `cycle_registry` (`registry_version` = the export's semver) and adds the runtime columns. 3. **Planning is idempotent per (cycle, period, unit).** For each active cycle the planner derives the window from the planned instant (rule 10's `as_of`, never `clock.now()` read twice), the period keys due in that window from `period_grammar`, and for each `(cycle_code, period_key)` inserts one `cycle_runs` row (`ON CONFLICT (cycle_code, period_key) DO NOTHING`) and one `jobs` row per selected unit (`ON CONFLICT (idempotency_key) DO NOTHING`), `blocked` when `depends_on` is unmet else `queued`; a new run appends `cycle.run.opened` (arming `SM_CYCLE_RUN_STALLED_1D`); the same window planned twice adds no row and no event (T2). The planner then reclaims leases (`running` with `lease_until < now()` → `queued`, `attempts` unchanged since the claim already counted it, `job.lease.expired`), unblocks jobs whose dependencies are now present, re-queues `failed` jobs whose `run_after` has passed, reconciles receipts (rule 5) and sets `overdue_since` on any active row whose `next_expected_by` has passed without a receipt (T11). It ends with one `cycles.plan.run_completed` (satisfying and re-arming `SM_CYCLE_PLANNER_DAILY`). Guardrail `PLAN_IS_IDEMPOTENT`.
4. **The planner is the month's clock.** On its first pass whose `as_of` civil date (America/New_York) is in a new month it appends `ledger.month.ended{period_key: <prior YYYY-MM>, period_end: <last day>}` on the global subject exactly once (a unique key on `(event type, period_key)` in `cycle_receipts`-style bookkeeping — `job_events{kind: planned, detail.period_key}` of the synthetic `month_end` unit) — the trigger 35.4's `SM_CLOSE_PERIOD_OPEN_BD1` arms on (T15). No emitter of this event exists today (verified above); this is it.
5. **The last unit elects the receipt, exactly once.** `cycles.run_unit` runs the unit's command through `Runtime.executeDef` under the unit's own scope (the loan, the application, or global) and, in that command's `opts.commit` hook (35.1's fact-projector phase — the same transaction as the unit's events, ledger sets, timers and decision), writes `jobs.status = done`, `decision_id`, the `job_events{done}` row and `UPDATE cycle_runs SET units_done = units_done + 1 WHERE id = $1 RETURNING units_done, units_dead, units_skipped, units_total`. If the returned counters sum to `units_total`, the executor opens a second, global unit of work that inserts `cycle_receipts{run_id}` (unique), appends the cycle's `receipt_event` literal (payload `{run_id, cycle_code, period_key, as_of_date, units_total, units_done, units_dead, units_skipped, outcomes_sha256}`) and `cycle.run.completed` (same payload plus `receipt_id`) on the `cycle_run` aggregate, and sets `cycle_runs.status = completed`. A crash between the two transactions leaves counters full and no receipt row; the planner's reconciliation (rule 3) finds every `running` run whose counters are full and no `cycle_receipts` row and emits the receipt with `emitted_by = planner:<run_id>`; the unique key makes a race between the executor and the planner produce one row and one pair of events (T5). Guardrail `RECEIPT_ONCE`.
6. **Executors claim, heartbeat and stop in time.** After planning, the sweep execution is the executor: it claims with `UPDATE jobs SET status = 'running', lease_holder = $holder, lease_until = now() + interval '5 minutes', heartbeat_at = now(), attempts = attempts + 1 WHERE id IN (SELECT id FROM jobs WHERE status = 'queued' AND (run_after IS NULL OR run_after <= now()) ORDER BY priority, created_at FOR UPDATE SKIP LOCKED LIMIT $n) RETURNING *` (`n` = 20), runs each claimed job through `cycles.run_unit`, heartbeats every 30 s (`heartbeat_at`, `lease_until` extended by 5 minutes), and stops claiming once 240 s of the job's 300 s timeout have elapsed (the demo advance's `DEFAULT_ADVANCE_BUDGET_MS` precedent, demo-clock.ts:62), releasing nothing it did not finish — an unfinished unit's lease expires by wall clock and the planner reclaims it. `lease_until` and `heartbeat_at` are wall time (`now()` in Postgres), never the demo clock, so an advance of 400 days cannot expire an in-flight unit (T10). Three claimants over one queue each take disjoint rows and no unit runs twice (T3). Guardrail `LEASE_IS_WALL_CLOCK`.
7. **JOB_RETRY, distinct from the outbox's policy.** `JOB_RETRY = { maxAttempts: 3, baseDelayMs: 60_000, maxDelayMs: 15 * 60_000 }` in `src/domain/operations-runtime/jobs.ts`: attempt 1 at claim, a throw → `failed` with `run_after = now() + 60 s`; attempt 2 → `failed`, `run_after = now() + 120 s`; attempt 3's throw → `dead` (`job.unit.dead`, arming `SM_JOB_DEAD_2H`, one escalation to the registry row's `escalation_role` with `{cycle_code, period_key, unit_id, error_class}`), and the run stays `running` (T4). A failure classified `unavailable` (the owning adapter's FAKE or real port down — the outbox's `FailureKind` vocabulary, outbox.ts:123) goes `dead` at once, as the outbox does, because retrying in a minute cannot help. `cycles.retry` (an agent's early retry of a `failed` job) consumes no extra attempt beyond the one it runs. A `dead` unit is requeued (`attempts` reset to 0, `max_attempts` 3 again) or abandoned only by `jobs.requeue` from an `ops_analyst`; an agent actor is refused `ROLE_REQUIRED` (T13). A unit's error message is stored; its input payload is not.
8. **A unit is its owner's command with its owner's actor and its owner's idempotency.** `cycles.run_unit{job_id}` reads the job, looks up the def, builds the actor `{kind: "agent", id: <owner_agent>}`, derives the unit's facts server-side inside the command (35.5's `LoanCashState`, 35.1's hydration) — the job's `input` carries ids and dates only; an `input` that carries `state`, `custodial`, a `*_cents` field or a `changes` object is refused `NO_CLIENT_STATE` before anything is written (T13) — and runs the runner. The runner's own idempotency governs: 2.1 posts by payment id, 7.1 opens one cycle per `(loan_id, cycle_due_date)` (T9), 8.1 builds one snapshot per `as_of_date`, 5.1 allocates sequences per loan and drops duplicate keys (batch.ts:1-25). One `agent_decisions` row per unit `{agent: <owner_agent>, action: cycles.run_unit, subject_kind: <cycle_code>, subject_id: <unit_id>, rule_set_version: cycles.v1, model_version: deterministic, prompt_version: 35.3-v1, confidence: 1, rationale: "<cycle_code> <period_key> unit <unit_id>: <runner outcome>"}` plus whatever decisions the owner's command writes. §7 and §8 units, whose spec tool lists are empty, run on the bus only this way; their spec files are untouched.
9. **The breach pass is paged.** After the executor budget, the sweep runs the breach pass in pages: `SELECT * FROM timers WHERE status = 'armed' AND due_at <= $1 ORDER BY due_at LIMIT 500 FOR UPDATE SKIP LOCKED` (35.1's clause on timers.ts:52-54, plus the `LIMIT`), one `db.tx` per page, until a page comes back short; 10,000 due timers produce 20 transactions and exactly the breaches a single pass would have produced, each once (T7). A page's transaction is the existing body (app.ts:280-297): restore into a fresh engine, evaluate, append `timer.breached`, save, open one escalation per breach.
10. **The demo advance runs the planner and the units inline, from the persisted offset.** For each crossed day the advance (demo-clock.ts:251-261) calls `OffsetClock.refresh` (:84-88), then `cycles.plan{as_of: step.at}` — the window's `as_of_date` is the step's ET civil date, `cycle_runs.demo_offset_ms` is the row's `offset_ms` (:117-121) — then drains the day's `queued` jobs to completion inline (no 240 s budget: the advance has its own, :62, and stops between steps, never inside one), then `Runtime.sweep(step.at)` for the breach pass; a three-day advance yields three `cycles.plan.run_completed`, one run per daily cycle per day with `period_key` = that day, and every receipt before the next step's plan (T8). The sweep job, which reads the offset once at start (main.ts:54-55), also `refresh()`es inside `cycles.plan` so it never plans a day the API has advanced past. In production `demo_offset_ms = 0` and `as_of` is the wall clock.
11. **A never-run cycle is a registry finding, not a clock.** The engine arms only on a trigger event (engine.ts:175-182); a cycle with no run has emitted nothing, so no timer can name it. The planner computes `next_expected_by` from `expected_by_rule` and the calendar and sets `overdue_since` when it passes with no receipt; `cycles.registry{op: list}` returns those rows first; 35.11's steward opens the escalation and owns the follow-up (T11). Guardrail `NO_SILENT_CYCLE`.
12. **Nothing here moves money or edits a clock.** The planner, the executor, the receipt and the requeue write `cycle_registry`, `cycle_runs`, `jobs`, `job_events`, `cycle_receipts`, their events, decisions and escalations, and nothing else; a money field changes only inside the owner's command under the owner's rules and waivers (`officer`); a timer moves only through the engine on the owner's events (34.4 rule 1). `jobs.requeue` re-runs a unit; it never edits what the unit wrote. Guardrails `NO_MONEY_FIELD`, `NO_CLOCK_EDIT`.

- **`postgres`** (in-process; `pg_try_advisory_lock(35_003)` on a dedicated client for the planner; `FOR UPDATE SKIP LOCKED` on `jobs` and on the paged `timers` read; idempotency by `cycle_runs(cycle_code, period_key)`, `jobs(idempotency_key)`, `cycle_receipts(run_id)`; on outage the sweep fails closed — nothing planned, nothing claimed, 35.1's heartbeat clock is the alarm).
- **Cloud Scheduler / Cloud Run job** (35.1's; unchanged: `* * * * *`, 180 s attempt deadline, 300 s job timeout — the 240 s executor budget in rule 6 is the only coupling; a change to the timeout changes the constant, cited to run.tf:347).
- **The demo clock** (`src/runtime/demo-clock.ts`; `refresh()` before planning; the step body calls the planner and the executor inline — rule 10).
- No external adapter: every unit's outbound traffic is the owning section's, through 35.1's outbox and the FAKE ports (`printMail`, `edelivery`, `lsdu`, `metro2`, `custodian`, …), in every build stage.

- Events: `cycles.plan.run_completed`, `cycles.plan.skipped`, `cycle.run.opened`, `cycle.run.completed`, `cycle.run.cancelled`, `job.unit.claimed`, `job.unit.done`, `job.unit.failed`, `job.unit.dead`, `job.unit.resolved`, `job.lease.expired`, `ledger.month.ended`, and each cycle's receipt literal (rule 2's column) — all string literals in `cycles.ts` / `service.ts`.

- No document, no notice: §35 owns no `NTC_` code; a unit's documents and notices are its owner's.

#### AI agent design (AI-first)
`ops-steward` agent (tools: `cycles.registry`, `cycles.plan`, `cycles.run_unit`, `cycles.receipt`, `cycles.retry`, `cycles.escalate`, `jobs.list`, `jobs.requeue`, `writeDecision`). End-to-end: unprompted, every sweep and every demo step, the agent plans under the planner lock, claims and runs units through `cycles.run_unit` as the owning section's agent, elects receipts, reclaims expired leases, retries `failed` units when their `run_after` passes, marks never-run cycles overdue and escalates dead units to the registry row's role; it proposes nothing for a human except the dead unit itself (the escalation with the error class and the two choices, requeue or abandon) and a paused cycle's resumption; it never runs a unit whose input names state or money, never requeues or abandons a dead unit (an `ops_analyst` does), never edits a clock, never writes a money field, never completes a breach. Decision record schema `{subject_kind: cycle_code, subject_id: unit_id | run_id | job_id, action: cycles.run_unit | cycles.plan | cycles.retry | cycles.escalate | jobs.requeue, period_key, attempt, outcome, error_class?, by?, reason?, rule_set_version: cycles.v1, model_version: deterministic, prompt_version: 35.3-v1, confidence: 1, rationale}`. Guardrails: `LEASE_DIES_WITH_SESSION`, `PLAN_IS_IDEMPOTENT`, `RECEIPT_ONCE`, `LEASE_IS_WALL_CLOCK`, `JOB_RETRY_CAP_3`, `NO_CLIENT_STATE`, `ROLE_REQUIRED` (requeue, abandon, pause, cancel are `ops_analyst`), `NO_MONEY_FIELD`, `NO_CLOCK_EDIT`, `NO_SILENT_CYCLE`, `UNIT_RUNS_AS_OWNER` (an input naming an actor or agent to run as is refused). Escalations: `ops_analyst` for a stalled run, a dead unit of a non-money cycle and a missed planner day; `officer` for a dead unit of `remittance`, `form_496_monthly` or `metro2_monthly`; `fnma_portal_operator` for a dead `lar_daily` unit; `compliance` when a paused cycle stays paused past its next `expected_by` (35.11 raises it from `overdue_since`).

#### Edge cases and failure modes
- The planner lock is held by a killed execution whose client has not yet been closed by Postgres → the next pass appends `cycles.plan.skipped`; `SM_CYCLE_PLANNER_DAILY` breaches only if no pass completes all day; the lock clears when the server notices the dead session (`tcp_keepalives`, platform default) — recorded as an operational note, never worked around with a table row.
- A unit succeeds but the process dies before `opts.commit` → the whole command rolled back (35.1 rule 2); the lease expires; the unit re-runs; its owner's idempotency makes the re-run the first run.
- A unit's runner is missing (a def names a runner 35.4/35.5/35.9 has not landed) → the job is `dead` on its first attempt with `error_class: runner_missing`, escalated to `ops_analyst`; the registry row still lists the cycle so the gap is visible, not silent.
- A dependency event arrives after the run's day (the investor close slips to BD3) → the `form_496_monthly` job stays `blocked`; `SM_CYCLE_RUN_STALLED_1D` breaches on day 2 naming the run; 35.4's own chain clocks are the alarm for the close itself; when both events are present the planner unblocks and the unit runs.
- A registry def is paused mid-run → planned and queued jobs go `skipped`, running ones finish; the run is `cancelled` with the pauser and reason; the receipt is not emitted; `cycle.run.cancelled` cancels the stall clock.
- Two demo advances race on two instances → `OffsetClock.exclusive` serializes per instance and the planner lock serializes across them; the second finds every day planned (`ON CONFLICT DO NOTHING`) and every job done or claimed.
- `units_total = 0` (a daily cycle with no eligible unit) → the run is opened and completed in the same planner pass with a receipt of zeros; the receipt is still the day's evidence that the cycle looked.
- The executor budget expires with claimed units still running → they finish (the process is not killed at 240 s, only at 300 s); anything still running at 300 s loses its transaction, its lease expires, the planner reclaims it, `attempts` already counted the claim.
- A selector's query exceeds 30 s → the planner logs, skips that cycle for this pass (`job_events` gains nothing; the registry row gets `last_error_class: selector_timeout`), plans the rest, and `overdue_since` will name the cycle if it keeps failing.

### Open questions / decisions
1. Should a dedicated worker job (Cloud Run job with `task_count > 1`, or a min-instance worker service) replace the sweep execution as the executor? **Default: the sweep execution is planner and executor within its 240 s budget; a worker job is opened as a decision for 35.12 once measured queue depth exceeds what one execution drains in a day.**
2. Should 6.3's dependency literal be renamed to `fnma.reporting_period.closed` to match the spec, or the spec amended to `investor_reporting_periods.closed`? **Default: the build depends on the emitted literal `investor_reporting_periods.closed`; 35.4 decides the rename when it lands the close chain.**
3. Should `units_dead > 0` at abandonment still emit a receipt? **Default: yes — a receipt with `units_dead > 0` and the abandoned unit ids is evidence the cycle ran and what it did not do; a run never stays `running` forever.**
4. Should `cashiering_daily` be split into three cycles (posting, late charges, amount-change checks)? **Default: one cycle, three steps in one unit per loan, so a loan's day is one transaction — 35.5 may split it if a step's cadence differs.**
5. Should a paused cycle's missed receipts count as overdue? **Default: no while paused; `overdue_since` is set at the first `next_expected_by` after `resume`, and `compliance` is told by 35.11 when a pause outlives an `expected_by`.**
