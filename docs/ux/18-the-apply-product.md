# 18 — The Apply product: the door, the nine steps and the five tabs on `/app`

Build plan for Claude Code. Save as `docs/ux/18-the-apply-product.md`; `tools/import_ux.py` imports it as process **32.19** (§0.4). The product is the borrower surface on `/app` since 2026-09-16: a light door (welcome, "What is Supermortgage?", the account), then nine screens — goal, property, you, connect, details, questions, demographics, review, result — in one phone column, under five tabs (Apply, Chat, My Loan, Tasks, Account). It replaces the Thread + Record + action bar shell of docs/ux/01 §1 as the surface and changes nothing underneath: every value a screen collects is written by resolving the pending card the flows of 32.3 already send (once, on the addressed purchase, by `application.confirmField`); the DU moment of 32.18 runs itself; the vendors are the FAKEs of 32.17 rule 19, finishing on the tap. This chapter is the frontend brief of 2026-09-16 (`CLAUDE_APPLY_FRONTEND_BRIEF.md`) reconciled against the tree at `9e8c5c4`: §0 records what the brief got right, what it got wrong and the correction the build follows; §2 carries the owner's decisions of 2026-09-16 (`docs/decisions/2026-09-16-apply-product.md`). Nothing in sections 1–31 changes; the additions are declared in §4 as DELTA-31…DELTA-35 and nowhere else.

## 1. Principles (binding)

Brief §2, verbatim and numbered, then three the tree adds.

1. The old dark-mode user site is dead. None of the current front end survives as the product surface.
2. New UX sits on the **existing backend**. Do not rewrite API, auth, DU emit, preflight, or FAKE vendors.
3. Signup / signin happens **after** the “What is Supermortgage?” page.
4. After session: walk every prototype step for Buy **and** Refinance, plus any extra field DU preflight requires.
5. “My Loan” is empty. Later a partner book will fill it. Do not invent a funded loan.
6. Vendors stay FAKE (`INTEGRATIONS=fake`). Use `fake_complete: true` where the client already supports it.
7. Keep the lightweight / agentic feel: one phone column, short copy, few fields per screen, cards as the data protocol underneath, not as the visual language.
8. Chat does not commit underwriting facts. Apply does.
9. **No DU word on a screen.** None of "DU", "Desktop Underwriter", "Fannie", "Approve", "Eligible", "Ineligible", "Refer" in any `apply.*` copy key or any string an Apply screen renders (README binding rule; 32.18-T6 / T8; `serialize.ts` keeps findings off `/v1/borrower/*`). Review and Result read `record.status.badge` and the copy library's lines and never name the run.
10. **Every string a copy key.** Every string the Apply screens render is a key of docs/ux/12 — a new `apply.*` family, the prototype's words as the text — rendered through `lib/copy` (32.1 §7.4; 32.13-T13 / T14 run over the new keys); no `.tsx` under `components/apply` contains a sentence literal; an API error renders `copy(copy_key)`, never a code.
11. **Cards are the data protocol.** A screen's fields are the pending card's fields; Continue resolves that card with `{evidence, option_id?}` — the exact shape the API reads — and the flows of 32.3 send the next card. The one command a screen posts is `application.confirmField{path: property_address}` on the addressed purchase, where no home card exists; nothing else is posted as a command from a screen, and Chat posts `POST /v1/borrower/messages` only. A value typed before its card exists waits in the draft and is written when the card arrives (§3.0).

How to read 5 and 8 after the owner's decisions of 2026-09-16 (§2.4): principle 5 means the page invents no loan — a party with a loan subject (a partner-book borrower, 33.x) sees that loan on My Loan from day one, because the record is read, not invented; a party with no loan subject sees `apply.loan.empty`. Principle 8 means the page never posts a command or resolves a card from Chat; the turn behind Chat keeps 32.16 rule 21 (words commit through the turn's own tools) and the page shows the receipt as the task done.

## 2. The product

### 2.0 One tree, one column
One component tree; no Next.js route per step; steps are React state (`components/apply/ApplyProduct.tsx`, one `export function ApplyProduct({ initialCard })`). The chrome is brief §6:

```
.sm-proto > .sm-phone
  header.sm-top     italic "s" mark + "Supermortgage" pill (tap → Apply / welcome)
  main.sm-stage     the current screen
  footer.sm-dock
    .sm-composer    only when tab === "chat"
    nav.sm-tabs     Apply | Chat | My Loan | Tasks | Account
  footer.disclosure on every screen, the door included (32.16 principle 8; owner decision 4)
```

The tokens are `apply.css`'s (accent `#bf242b`, pressed `#aa1d24`, soft `#f9e1e2`, paper `#fcfcfc`, bubble `#eaeaea`, text `#080808`, muted `#68686a`; the mark italic 48px Georgia; the column `max-width: 430px` on `.sm-phone`; `.sm-primary` the red 44px pill; `.sm-choice` dashed with `.selected`; `.sm-tabs` the five-column 62px pill). The old dark tokens of `globals.css` never leak onto `.sm-proto`; the dark set stays beneath, selected by `data-theme` (32.1 §2 as amended). At 390 px the five tabs and the primary CTA are in the viewport and `document.documentElement.scrollWidth ≤ 390`; at 1280 the column is 430 px on the paper.

State: `tab ∈ {apply, chat, loan, tasks, account}`, `door ∈ {welcome, intro, account}`, `step ∈ {goal, property, you, connect, details, questions, demographics, review, result}`, `TaskId = Exclude<Step, "goal" | "result">` (the seven tasks), a `Draft` of typed values, and `me`, `record`, `cards` from the API. `done[taskId]` is derived from the record and the card statuses on every render, never remembered (§3.0).

## 3. Wiring

### 3.0 The resolve-first rule and the mechanics every screen shares
- **Boot.** `api.me()` → `me`; `applicationId = me.subjects.find(s => s.application_id)?.application_id ?? null` — poll `me` for up to 30 s after an account door until a subject appears (`landSession` creates the organic application; a loan-only party has none); `refresh()` = `me` + `record(subject)` + `thread().cards`.
- **`resolveFirst(key, evidence, fallback?)`.** `const card = pending(cards, key)`; if the card exists → `api.resolveCard(card.card_instance_id, {evidence, option_id?})`; else if a `fallback` is given → `api.command(fallback.name, {application_id, ...fallback.args})`; else hold the values in the draft; then `refresh()`. The evidence shapes of §3.1 are the exact ones the API reads (`body.evidence.fields`, `body.option_id`). `pending()` matches `copy_key === key` exactly, never `startsWith`, so the `declarations.*` family resolves one card at a time.
- **`waitForCard(key, ms)`.** Poll `thread()` until a pending card with `copy_key === key` exists — the flows react asynchronously (`du-journey.mts`'s `waitForCard`).
- **Vendor sessions**, always with `fake_complete: true` (a real vendor ignores it, `client.ts:93-95`): `api.identitySession({application_id, fake_complete: true})` on the pending `identity.stripe.purpose`; `api.connectSession("truv_income" | "plaid_assets", card.card_instance_id, {fake_complete: true})` on the pending `income.connect.purpose` / `assets.connect.purpose`. The route resolves the card and orders 22.3 / 22.4 itself. The page never posts `verification.connect`.
- **Errors.** `ApiRequestError.body.copy_key` → `copy(copy_key)` (fallback `error.generic`) into `<p class="sm-error" role="status" data-testid="apply-error">`; never the raw code. A `409 CARD_FIELD_REQUIRED` stays on the step. No `.catch(() => undefined)` anywhere. A required field empty stays on the step with `.sm-error` and posts nothing.
- **Copy.** Every rendered string is a copy key — the `apply.*` family in docs/ux/12 (`npm run gen:copy`), the prototype's words as the text (`apply.door.tagline` "The Self-Improving Mortgage", `apply.goal.question` "Are you looking to:", …). No "DU", "Desktop Underwriter", "Fannie", "Approve / Eligible / Refer" in any key.
- **The goal tap is Property's Continue.** The goal card's tap carries the property (`args.property`), so the tap that resolves `entry.goal.question` is the Property screen's Continue on every branch; the Goal screen only sets the draft. The consents statement renders above that Continue; Review's fine print repeats that the three consents were written at that tap.
- **Draft and flush.** A value typed before its card exists is held in the draft and written by the next step's `flush()` when the card arrives (the refinance address → `refi.home.confirm`; price / value / balance → the number cards on Review). Nothing is written by a path 21.1 stores as free text.
- **`done[taskId]` is derived, never remembered**: property = the goal card resolved and (the `property_address` six-item captured or `preapproval.where` resolved); you = `identity.ssn.title` resolved; connect = income captured and the plaid card not pending; details = `profile.title` resolved; questions = `application.declarations.answered`; demographics = `demographics.title` resolved; review = the number cards resolved. The six-item state comes from `record.needed_from_you` and the card statuses (the events are not on `/v1/borrower/*`).
- **`cents()`** converts a typed amount to an integer string without floats (split on the point, pad, `BigInt`) — 32.13-T9 and `lint-money`.
